Preview — as a friend

SPEC §9.5, mode 1: the owner can preview their own profile and contact card exactly as one specific friend would see them. This mode exists because both surfaces are per-friend — the contact card follows the per-friend visibility cascade of §10.3, and the mutual-friend block on the profile itself depends on who is looking — so only naming a friend makes either concrete.

The report actions render, and they do nothing — §13.2 in terms: "In preview-as the action renders and does nothing." The preview is a truthful rendering of the surface a friend sees, so hiding them would misrepresent it, and preview mode is already strictly read-only; §9.5 adds no special case. Note what looks like a contradiction and is not: §13.2 says the report action is never shown to the card's owner, and this page shows it to David. It is not a violation, because David is previewing rather than reporting — the buttons are Alice's, rendered so David can see what she sees. Preview-as changes who is looking, never what they would see.

The last two items are new in R3, matching the card page item for item — the two pages must not disagree about what the same card looks like. The WhatsApp item is now a real hyperlink: messenger domains are allowlisted with card scope as of v1.29 (§7.2.3), so the same address in a post would be a copy box. M4 rendered it as the obfuscated string wa dot me slash […], which was the pre-1.29 rendering.
