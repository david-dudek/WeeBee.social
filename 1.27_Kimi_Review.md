# WeeBee design review (v1.27)

**Overall impression, for context:** this is an unusually disciplined set of documents. The stack choices are sound, the ops reasoning is honest (24‑hour backup-loss window stated in plain text, backup key kept off-server, restore rehearsals that must use the off-server copy, silent cron-failure monitoring), and the project already runs a self-review process most professional teams skip. I found **no hallucinated technology** — every tool, API, and WCAG criterion referenced is real and described accurately (HIBP k-anonymity, the `google.com/url?q=` redirector, crt.sh, WCAG 3.2.2/2.2.2, etc.). The problems that exist are of a different kind: a handful of genuine internal contradictions (one introduced by the newest version), several over-broad absolute claims, and a large *known* staleness backlog in two of the four law files.

I'll separate what the documents **don't** know about from what they **do**, because that distinction is the real story here.

## Part 1 — New issues in SPEC.md (the authoritative document)

### 1.1 The feed lists "warnings" that the newest version just abolished — **SPEC.md §7.7 vs §13.2.1 and §12.1** ⚠️ the sharpest finding

§7.7's feed-contents sentence still reads: *"system notifications (friend requests, introductions, contact-card events, **warnings**)."* But v1.27 (§13.2.1) explicitly **rejected** an in-feed warning type — operator warnings are email-only — and §12.1 was updated to say *"an operator warning (email only… deliberately not an in-feed type)."* Inactivity warnings (§4.8) are email-only too, so the "warnings" in §7.7 now refer to a notification type that does not exist anywhere.

**Layman:** the newest edit removed warning messages from the feed everywhere except one sentence it forgot. A builder following §7.7 would build a feed feature the same document elsewhere forbids. Notably, the v1.27 changelog claims the only list that needed updating was §12.1's — §7.7 slipped through the project's own net, which is worth noting precisely because the net is good.

### 1.2 The name-change guarantee is false for pinned posts — **SPEC.md §4.5.1**

§4.5.1 justifies the 90-day "formerly" tag with: *"every post ever seen under the old name expires before the tag comes off."* But pinned posts **never expire** (§7.6). A pinned post seen under the old name is still standing when the tag comes off, so the stated invariant simply isn't true for the one class of content that can live forever.

**Layman:** the document promises "by the time your old name disappears, everything anyone saw under it has also disappeared" — but the keep-forever posts break that promise. The practical harm is small (names render live, so nothing shows a *stale* name), but the guarantee as written is wrong, and it's the kind of absolute sentence this project elsewhere prides itself on only writing when true. One clause — "every post except pinned ones" — fixes it.

### 1.3 The notification examples break the rule they sit under — **SPEC.md §12.2 (and §12.3), echoed in BUILD_PLAN.md Step 12.2**

§12.2's rule: *"Names, never numbers… never '3 new comments'."* Two bullets later, its own examples read *"David added **3** photos to his gallery"* and *"David posted **twice** to his blog."* Both display counts. §7.7.1 refuses even "Page 3 of 7" as *"a post count wearing different clothes"*; §17 makes post counts a non-goal; and §12.2's own rationale — stopping a private count from *"becoming a score comparable across one's own posts"* — is exactly what "posted twice" invites. BUILD_PLAN Step 12.2 repeats the "posted twice" wording, so the defect is queued to propagate into the actual UI copy.

**Layman:** the style guide says "never show numbers," then shows numbers in its own examples. Either the examples change ("David added photos to his gallery") or the rule needs a written carve-out for object counts. As written, an AI builder has to guess which instruction to follow.

### 1.4 The "preview as a friend-of-friend" picker is missing the tags that matter — **SPEC.md §9.5 mode 3**

Mode 3 offers a picker over *"the tags present on the owner's own profile and pinned posts, which is **the only set that can change the result**."* That claim is wrong. The §11.3 hashtag gate applies to **every** profile post, pinned or not — and mode 3 itself says it renders *"the Blog and Pinned tabs filtered exactly as §11.3 will filter them."* A tag that appears only on an ordinary, unpinned blog post changes what a friend-of-friend carrying that tag sees on the Blog tab — but the owner can't select it in the preview, because the picker omits it.

**Layman:** the "see my profile as a stranger with interest X sees it" tool can't simulate a stranger whose only shared interest appears in one of your everyday (non-pinned) posts. The feature exists precisely to show the owner what others see, and it has a blind spot in exactly the case it claims is impossible. The fix is to draw the picker set from profile + **all live profile posts**, or to state the limitation honestly.

### 1.5 "The architecture deliberately does without JavaScript" is not true — **SPEC.md §7.7.1**

§7.7.1 argues against infinite scroll with: *"Both need JavaScript, which the architecture deliberately does without (§16.2)."* But ARCHITECTURE.md §3.5 specifies five hand-written JavaScript "islands" (the audience picker's live count, the searchable hashtag picker, contact-card toggles, image-upload preview, the group-save prompt), names htmx as the approved escalation, and §3.8 specifies ARIA behavior for those islands. Even SPEC's own §16.2 — the section cited — says only *"no JavaScript **framework**,"* and §16.3's expanding "read more" button (`aria-expanded`, focus retention) is JavaScript behavior.

**Layman:** one document claims "we use no JavaScript at all" while the architecture document plans several small JavaScript features. The accurate claim — *no framework, and every page works without JavaScript* — is actually the stronger statement and is already written down elsewhere. As it stands, a builder could read §7.7.1 as forbidding the very islands §3.5 requires.

### 1.6 "Venue and restaurant pages" can't pass the anti-phishing bar — **SPEC.md §7.2.3**

The allowlist's category 1 admits *"venue and restaurant pages,"* but the mandatory bar two paragraphs later requires *"official domains of **large, stable, non-deceptive services** only."* A neighborhood restaurant's own website is not a large, stable service. Either the bar silently excludes the category's most common case (making "venue and restaurant pages" nearly empty in practice), or small-business sites are an unstated exception — which weakens the anti-phishing control with exactly the class of domains most likely to be abandoned, expired, or hijacked.

**Layman:** the rulebook says "you may link to the restaurant's website" and also "only big, well-known websites allowed." Those two sentences can't both be enforced. One sentence saying which wins — e.g., "convening means maps, RSVP and ticketing *platforms*" — resolves it.

### 1.7 The GDPR export omits two newer kinds of data — **SPEC.md §4.9**

The export lists profile, posts, authored comments, friend list, groups, contact card, and images. It does **not** include the user's own **reactions** (statements attached to their name, stored with their own `set_at` clock per §8.2.1) or the **moderation records** v1.27 just added (§13.4: ban state, and the texts of warnings sent to the account). Since §4.9's first stated purpose is GDPR compliance, the omissions matter — both are personal data, and reactions are arguably the user's own authored statements.

**Layman:** the "download everything you have on me" file is missing two things the platform has on you. One line in §4.9 fixes it; the data model already stores both.

### 1.8 Invite replenishment has an undefined edge case — **SPEC.md §4.2**

*"+1 every 30 days **since the last replenishment**, never exceeding the bank max."* What happens when the bank is full? Reading A: the 30-day timer keeps ticking and the credit is lost (the standard "energy timer"). Reading B: no replenishment *happens* at the cap, so the clock goes stale — and the day a user spends one invite, it's been far more than 30 days "since the last replenishment," so they immediately get it back, making the 5-invite cap nearly toothless for regular inviters.

**Layman:** the rule doesn't say whether a full invite bank pauses the refills or wastes them. Two reasonable builders will build two different systems from this sentence, and one of them quietly removes the anti-abuse point of the cap.

### 1.9 Discovery ranks people by the numbers the platform refuses to show — **SPEC.md §11.4** (minor tension, not a contradiction)

Discover ranks suggestions *"by shared mutual friends and shared profile hashtags"* — counts — while §11.5 forbids displaying those very counts and §17 declares counting a non-goal. This is defensible (some ordering must exist; §7.7's "no algorithmic ranking, ever" is explicitly feed-scoped), but it is the one place the platform sorts humans by a number, and the sort order itself leaks the variable. A single sentence acknowledging the carve-out would prevent a future builder either ripping it out as a violation or extending it into something worse.

## Part 2 — New issues in ARCHITECTURE.md

### 2.1 The email section contradicts the same document's cost table — **ARCHITECTURE.md §3.6 vs §11, and BUILD_PLAN.md §5.1**

§3.6's provider requirements still say *"low/**free tier** at our volume (hundreds of emails/month)."* §11's cost table says *"**the free tier does not cover launch volume**; budget the paid step from the launch month,"* and BUILD_PLAN §5.1 spells out why (the free 100-emails/month tier is spent within weeks). §3.6 also still promises *"verification **links**,"* although SPEC §4.6.1 has mandated codes-not-links since v1.8 — and "we never email login links" is a published, checkable promise the document elsewhere treats as load-bearing.

**Layman:** the architecture chapter says email will be free and will contain links; the same file's budget chapter says it won't be free, and the spec forbids the links. Stale leftovers from earlier versions — cheap to fix, and exactly the class of thing the project's own sync process (below) exists to catch, though these two lines don't appear in the sync's inventory.

### 2.2 The belt-and-braces URL rule will refuse some innocent links — **ARCHITECTURE.md §7.1** (minor)

*"Any allowed URL whose query string contains an absolute `http(s)://` URL is refused regardless of host."* Good defense against open redirectors, but it will also catch legitimate deep links (some ticketing and calendar services embed return URLs). Because §7.2.3's refusal message points the user at their contact card, the cost of a false positive is low — but the rule should be documented as a blunt heuristic with expected false positives, not as precise.

**The practical consequence, in layman's terms:** the instruction manuals a builder would actually work from (ARCHITECTURE, BUILD_PLAN) are currently twelve versions behind the rulebook (SPEC) in specific, itemized places. If the founder follows their own process and runs the prompt-09 sync first, this is a queue, not a hazard. If anyone starts building against today's files, they *will* write code the current spec forbids and omit code it requires — the documents themselves predict this and name the steps where it will happen.

## Part 4 — Pitfalls that are neither contradictions nor staleness

1. **The founder-verification blind spot is real and admitted.** BUILD_PLAN.md §0.6 states plainly that the conformance check cannot catch *"a test that cites the right section and asserts the wrong thing."* Every guard (deny rules, pre-commit hook, checksum tripwire) protects the five law files; nothing equivalent protects the *code*. A non-developer founder is the final verifier of AI-written code. This is the project's single largest structural risk, and the documents deserve credit for writing it down — but a reader should not mistake the impressive process machinery for a guarantee of code correctness.

2. **The WCAG 2.1 AA claim is the strongest promise in the documents and the least fully within the project's control.** SPEC §16 makes conformance *"a requirement of the same rank as the tracking ban."* The design genuinely helps (server-rendered native elements, contrast tests, five-pass audit, a booked external tester), but "conformance" is a formal, testable claim that a solo founder plus automated checks plus one audit typically only partially substantiates. The public accessibility statement (Step 15.2) should claim "designed and audited against WCAG 2.1 AA" rather than flat conformance, unless the external audit is real and passes.

3. **Solo-operator sustainability.** Every recovery path ends at one person: reading the weekly digest, noticing when it *doesn't* arrive, moderating the report queue, answering domain requests, rehearsing restores. The documents are honest about this (ARCHITECTURE §13.3: "the true bottleneck at scale is human moderation time, not hardware"), and the interim monitoring gap (a watchdog that cannot report its own death) is consciously accepted with a named trigger to fix it. This is fine — as long as the founder's interest outlasts the novelty.

4. **The visibility engine is where the bugs will live.** Six functions, each rule expressed twice (SQL for lists, Python for items), kept in sync by one equivalence test, with a request-scoped cache keyed on the viewer and flushed on any write. The design is correct and the tests are the right ones — but this is the one component where a mistake is a *silent privacy leak*, indistinguishable from correct behavior, by the architecture's own admission (§7.1). It deserves the disproportionate test weight §9 gives it, and arguably an external security review of that module alone before any public phase.

## Part 5 — Can this be built as described?

**Yes — I assess the likelihood as high (roughly 70–80%) that the v1 prototype ships and works as specified, conditional on three things:**

1. **Prompt 09 runs before Phase 2**, as the project's own tracker demands. This is the single gating precondition; everything in Part 3 is known-wrong until it does.
2. **The external verifications actually happen** — the accessibility tester (Step 15.3), the pre-launch audit (16.5), the deliberate-breakage tests (16.6). The plan books them; plans like this usually die by quietly skipping exactly these steps.
3. **The founder sustains the weekly operational rhythm** the design depends on (digest, moderation, restore rehearsals).

**Why the odds are good:** the technology is deliberately boring — Django, PostgreSQL, Caddy, Gunicorn, Docker, cron, Pillow on a single VPS. Every component is mature, massively documented, and heavily represented in AI training data, which is the ideal substrate for AI-assisted development by a non-developer. The feature surface is small by design, the scaling targets are modest (the documents' own arithmetic: disk, not CPU, breaks first at ~500 users), and the process discipline — versioned law files, itemized known-defect queues, external reviews that have already caught real contradictions — is genuinely better than most professionally-run small projects.

**Why the odds aren't higher:** the correctness of the visibility engine rests on tests whose semantic rightness no automated check can confirm (§0.6's admitted blind spot); the WCAG conformance claim may need softening; and the two instruction documents a builder would read today are twelve versions stale in itemized places. None of these is fatal; all of them are manageable; and the project is one of the very few I've reviewed that has already written down most of its own weaknesses — including, as of v1.27, three contradictions that two other AI reviewers certified did not exist.

The critique's shortest form: **fix the eight SPEC issues in Part 1 (they're one editing session), run prompt 09 before writing a line of code, and treat the accessibility claim and the founder-verification gap as the two honest risks the design can't engineer away.**
