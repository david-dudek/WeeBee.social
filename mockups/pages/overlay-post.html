Post image overlay, open

The same click-to-expand overlay of §7.2.2, reached this time from an image inside a post rather than the gallery — David's tomato photo on the Blog tab. The two variants differ in one way only: from a post, there are no next/previous controls, since a post carries at most one image and there is nothing to step between.

The page behind the dialog

Dimmed and inert while the dialog is open. The post below carries the ordinary, uneventful case of SPEC §7.2.4 — one address on neither link list, rendered as an inert copy box with the address in full and verbatim, no hyperlink, and nothing flagged. It also shows what the overlay does to that control: §16.3 traps focus inside the dialog while it is open, so the copy button here is genuinely unreachable until the dialog closes. That is why this container carries inert alongside the aria-hidden it already had — until this session the backdrop held no focusable element at all, and a focusable control inside an aria-hidden region on its own would be a 4.1.2 failure rather than a faithful drawing of a focus trap (see mockups/NOTES.md). The many-controls demonstration §16.3 asks for lives on the feed-post view instead, which is the single-post view that actually carries comments; this page is the image overlay.

The dialog, open

Same obligations as the gallery variant (§16.3, §7.2.2): focus moves onto the dialog on open, is trapped inside it while open, Escape closes it, and focus returns afterward — here, to the image inside the tomato post. No Previous/Next controls exist on this variant, since a single post's one image has nothing to step between. The alternative text renders as a visible caption, with the image's own alt left empty (§9.4).
