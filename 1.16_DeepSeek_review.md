# Project Documents Critique

I've read through all four documents carefully. Here's my analysis of the pitfalls, inconsistencies, and potential issues.

---

## README.md

### 1. The Feedback Mechanism Is Awkward
**Section:** "How to give feedback"

The README says "Please don't send pull requests" and describes a versioned design process on the founder's side—yet the file is in a GitHub repository. This creates confusion: if I'm one of the "few" people you share this with, what am I supposed to do? The instructions point me to a process that exists only in your head, not in the repository. This is a social friction point that will deter useful feedback.

**Recommendation:** Create a `CONTRIBUTING.md` or `FEEDBACK.md` that gives concrete instructions (e.g., "file a GitHub issue with the document and section number").

## SPEC.md — The Core Product Specification

### 2. Name vs. Handle Confusion (Major)
**Sections:** §4.5, §4.5.1, and many others

The spec says display names are "freely chosen, **no uniqueness requirement**, changeable." Then later (§8.1) it says commenter names link to profiles. If names aren't unique, how does the system know which "David" to link to? The architecture document (§4) says users are keyed by UUID, which is correct—but that means URLs to profiles probably use the UUID, not the name. The spec doesn't say this clearly, and a developer reading only the spec might try to use names in URLs, which would break.

**Recommendation:** In §4.5, explicitly state: "Profile URLs use the account's permanent internal ID (UUID), never the display name." Then in §8.1, say "the name links to `/profile/<uuid>/`."

### 3. Hashtag Vocabulary Is a Bottleneck (Operational Risk)
**Sections:** §11.2, §13.5

Hashtags are "never free-typed"—users can only pick from a single, operator-curated vocabulary via a searchable picker. Users can *suggest* new tags through the operator request form.

This means the operator (the founder) becomes the **single point of failure** for all hashtag creation. If you're on vacation, no new hashtags can be added. If users propose 50 tags in a week, you have to manually approve each one. This is the exact kind of operational burden that kills solo projects.

**Recommendation:** Add a "threshold" mechanism: after 3 users suggest the same tag, it auto-approves into the vocabulary. Or change the policy to allow free-typed tags that are only matchable if they're in the vocabulary (so people can type what they want, but discovery only works with approved tags).

### 4. The "Preformatted Posts" Exception Could Be Exploited
**Sections:** §7.2.1, §16.3

Preformatted posts:
- Preserve runs of spaces exactly (no collapsing)
- Never soft-wrap on narrow screens (horizontal scroll instead)
- Are **not** subject to normal whitespace normalization

This is designed for ASCII art and text tables. But an attacker could use this to:
- Post a 10,000-character line of text that forces horizontal scrolling on every reader
- Use spaces to create visual patterns that are actually harassment (e.g., building a rude shape out of characters)

**Recommendation:** Add a per-post "horizontal scroll containment" rule: the container must not exceed the viewport's width, and scrolling must be confined to the container. Also, consider requiring preformatted posts to have a "reason" or "description" field.

### 5. The "No-Reach" Guarantee Has a Weasel Clause
**Section:** §1.2

> "It is not a claim that an idea can never travel. A person can always read something here and retype it... That path is deliberately not designed against, because it is indistinguishable from a friend telling a friend about something."

This is honest, but it undermines the entire philosophical premise. If I can retype a post and send it to my 30 friends, I've just manually done what the platform refuses to automate. The platform can't prevent this, and acknowledging it is good—but the document should also acknowledge that this means the "anti-viral" design is only partially effective.

**Recommendation:** This isn't a problem to fix; it's a limitation to state up front. But consider adding a "copy protection" suggestion: perhaps watermarking or visible-from-text-only posts that make retyping obviously second-hand.

### 6. Editing Hashtags Is a Privacy Minefield
**Section:** §7.8 (Invariant 1's exception)

Editing a profile post's hashtags can **widen the audience** to new FoFs who share that tag. If the post already has comments, those commenters are notified that more people can see their words now. This is the right behavior, but:

- **What if a commenter no longer wants their comment to be visible to the widened audience?** They can delete it, but they only have 90 days (and after deletion it's gone forever). The notification gives them a chance to act—but if they miss the notification, their words are now visible to strangers who were in the original audience.

**Recommendation:** Consider adding an "opt-out" toggle: when a post's audience widens, commenters receive a notification with a "remove my comment from this post" action.

### 7. The "Friends Page" Filter Could Be Confused with Search
**Section:** §11.6

> "A filter box over that list. This is not the global search §17 forbids."

This is correct—but users won't distinguish between "search my 300 friends" and "search the whole network." The UI needs to be **very clear** that this only searches your friends. The spec should require a label like "Filter your friends list" rather than just "Search" or "Find people."

## ARCHITECTURE.md — The Technology Plan

### 8. The "One Server" Assumption Is Fragile
**Section:** §2 (Decision 2), §13 (Scaling)

The plan says one server is "not a compromise; it is the correct design." Then §13 describes how to scale to millions. The tension is that **if the platform succeeds, you have to do architectural surgery at the exact moment when you least have time for it**—when you're busy with users, moderation, and growth.

This is the classic "success is a failure" problem. You're building for a future you hope never happens (solo success) while claiming it'll work if it does.

**Recommendation:** This is honest, but the scaling section should be moved to a separate document (or an appendix) and the main architecture should say "We'll cross that bridge if we get to it." Right now it reads as defensive.

### 9. The "No Cloudflare Proxy" Rule Is a Security Risk
**Section:** §7 (Security Posture), §13.3

> "TLS may terminate only on machines this project administers."

This means you're exposing your VPS directly to the internet with no DDoS protection layer. Cloudflare's proxy mode (the orange cloud) is the single most common way small sites protect themselves from DDoS, and you're explicitly banning it.

**The risk:** A DDoS attack could take you offline for hours or days, and you have no mitigation plan other than "rent a bigger server" (which still gets overwhelmed) or "use a scrubbing service" (which costs money and takes time to configure).

**Recommendation:** Acknowledge this risk explicitly in the architecture and say "we accept this risk for v1." Or create a plan B: "If DDoS becomes a problem, we'll re-evaluate the Cloudflare ban."

### 10. The "Backup Retention" Tension Is Understated
**Section:** §10

> "Backups are kept 30 days, then destroyed. Deleted content therefore fully ceases to exist within at most 30 days of its deletion."

This is the standard solution. But it's also the **exact thing GDPR enforcement will check**: can you prove that content is deleted promptly? If a user requests deletion, and you show them a backup that still contains their data (even encrypted), you might be in violation.

**Recommendation:** In the GDPR/legal discussion (§15.1), explicitly mention that backups are encrypted and that deletion is "complete" only after the backup retention window. Or consider backup encryption with a key that's rotated and old keys destroyed, so old backups are unreadable.

### 11. The "Email Provider" Setup Is Not Trivial
**Section:** §3.6, BUILD_PLAN.md §5.5

> "Choose Postmark, Mailgun, or Amazon SES."

Postmark (recommended) requires DNS setup (SPF, DKIM, DMARC). But **SPF and DKIM are easy to misconfigure**, and DMARC at `p=reject` means your emails will be completely rejected if the setup is wrong.

**Recommendation:** In BUILD_PLAN.md §5.5, add explicit "verify" steps:
- "Send a test email and check the Postmark dashboard—it should show delivered."
- "Use MXToolbox or a similar tool to verify your SPF/DKIM/DMARC records."
- "If DMARC is at `p=reject`, test with `p=none` for 48 hours first."

### 12. The "Django Admin" Is Not WCAG AA
**Section:** §16.1

> "The operator console (Django admin) is held to the same standard as far as the framework allows; where it falls short, the shortfall is the operator's own, not a user's."

This is a cop-out. The Django admin is notoriously inaccessible in certain ways (e.g., complex table layouts, inconsistent labeling). If you're going to make accessibility a "requirement of the same rank as the tracking ban," you need to either:
1. Build your own admin interface (extra work)
2. Accept that the operator console is an exception

**Recommendation:** Either explicitly say "The Django admin is exempt from the WCAG AA requirement, because it's only used by the operator," or commit to building a custom admin that's actually accessible.

### 13. The "Dependency Approval" Rule Is Inconsistent
**Section:** BUILD_PLAN.md §2.5, Appendix rule 6

> "No new dependencies without founder approval. The one pre-approved addition is `argon2-cffi`."

But `argon2-cffi` is a **required** dependency for Argon2id password hashing, which is a **requirement** in SPEC.md §4.6.1. So it's not a "new dependency" if the architecture forces it—it's a dependency that was implied by the spec and should have been in the stack from the start.

**Recommendation:** Move this to ARCHITECTURE.md §3 (the stack) so it's clear that `argon2-cffi` is part of the base stack, not an "exception."

## BUILD_PLAN.md — The Construction Plan

### 14. The "One Step at a Time" Rule Is Good, But...
**Section:** §0.2

> "One step at a time, in order. Steps are sequenced so that everything a step needs already exists."

This is a classic project management approach, but it assumes that **everything you'll need in step 12 is known at step 1**. In practice, you'll discover missing steps as you build.

**Recommendation:** Add a "discovery loop" rule: "If you discover a missing step, add it as a new numbered step (e.g., Phase 6.2a) and re-run the preceding verification. Never skip ahead to unblock yourself."

### 15. The "AI Never Edits Law Files" Rule Is Naive
**Section:** §0.2 rule 5

> "The AI never edits SPEC.md, ARCHITECTURE.md, this file, or the values in constants.py."

But then BUILD_PLAN.md §0.2 says "If a step seems to require changing any of those, stop—that's a design conversation." This assumes the AI will recognize when it needs to change a law file. It won't. The AI will generate code that violates the spec, and you'll have to manually fix it.

**Recommendation:** The mechanical guards (pre-commit hook, tripwire tests) are good. But also add a verification step: "After each phase, manually compare the database schema and code behavior to SPEC.md. This is your responsibility, not the AI's."

### 16. The "Pre-commit Hook" Security Is Weak
**Section:** §2.4

> "A git pre-commit hook refusing any commit that touches a law file; overriding it requires a deliberate founder act."

A pre-commit hook can be bypassed with `git commit --no-verify`. If you're using an AI assistant, the AI could theoretically learn to use `--no-verify`.

**Recommendation:** Also use a **server-side** git hook (GitHub Actions) that rejects any PR that touches the law files. This is a much stronger lock.

### 17. The "Contrast Test" Is Not Enough
**Section:** §8.2, §16.5

> "Every THEME_SET combination's text and UI-boundary token pairs are computed against WCAG 2.1 AA ratios."

This tests contrast, but not:
- Focus order and visibility
- Keyboard operability
- Screen reader announcements
- ARIA attributes
- Error message associations

**Recommendation:** Add "automated accessibility audits" as part of the CI/CD pipeline. Tools like `pa11y-ci` can be run as a GitHub Action. But the founder's manual testing is the real gate—the spec acknowledges this in §16.5.

### 18. The "Restore Rehearsal" Is Only Done Twice
**Section:** §5.6, §16.4

> "Restore is rehearsed once during setup" and "Restore rehearsal #2."

Backup restores are the exact kind of thing that works during setup and fails at 2 a.m. on a Sunday when the server has crashed.

**Recommendation:** Automate the restore test: a weekly job that restores the backup to a test environment and runs a smoke test. If it fails, you get an alert during normal working hours.

### 19. The "Phone Browser Test" Is Incomplete
**Section:** §2.5

> "On your Mac and on your phone's browser... log in, log out, reset your password."

But you're testing on a phone you control. You haven't tested:
- Different screen sizes (tablets, large phones, small phones)
- Different browsers (Safari, Chrome, Firefox)
- Low-bandwidth or high-latency connections
- Offline mode (the login page should fail gracefully)

**Recommendation:** Add a "browser compatibility matrix" to the test plan: Safari (macOS and iOS), Chrome (macOS and Android), Firefox (macOS). Test at 320px, 375px, 768px, and 1024px widths.

### 20. The "Inactivity Sweep" Email Timing Is Ambiguous
**Section:** §6 (Housekeeping jobs), §14

> "Send 6/12/22/23-month warnings; delete at 24 months."

But what is "month" in this context? Calendar months? 30-day chunks? The spec says `CONTENT_TTL_DAYS` = 90, but the inactivity policy says "months" in prose.

**Recommendation:** Define `INACTIVITY_MONTHS` as a constant in `constants.py` with a comment: "defined as 30 days, not calendar months."

### 21. The "Email Provider Free Tier" Risk
**Section:** §5.5

> "Postmark free 100 emails/month covers the prototype."

Postmark's free tier is 100 emails/month. If you have 20 users who each send 5 emails (invites, resets, etc.), you're at 100. You'll hit the limit quickly during testing.

**Recommendation:** Choose a provider with a more generous free tier (e.g., Amazon SES is pay-as-you-go and cheap) or have a plan B ready.

### 22. The "Accessibility Audit" Is Not Automated
**Section:** §16.5

> "Keyboard-only pass," "Screen-reader pass," "Zoom and reflow pass."

These are manual. They'll only happen **once** before launch. But accessibility regressions are common after code changes. If you add a new feature in Phase 17, you won't re-test accessibility.

**Recommendation:** Add accessibility tests to your CI pipeline: `pa11y-ci` for automated scanning, and a GitHub Action that runs the keyboard test (there are automated keyboard-only testing tools). The founder's manual audit is still valuable, but it shouldn't be the only gate.

## Cross-Document Inconsistencies

### 23. `COMMENT_LENGTH_MAX` Is Marked as ✎ But Not Defined in BUILD_PLAN
**SPEC.md §14:** `COMMENT_LENGTH_MAX` is marked ✎ (operator-tunable).
**BUILD_PLAN.md:** No step sets this constant. It's mentioned in §2.1 (`constants.py`), but the value isn't specified.

**Recommendation:** In BUILD_PLAN.md §2.2, explicitly say: "Set `COMMENT_LENGTH_MAX` to 2000" (the default from SPEC.md §14).

### 24. The "Friends Page" Is Added in SPEC v1.16, But BUILD_PLAN Has No Step
**SPEC.md §11.6:** "The friends page" is new.
**BUILD_PLAN.md:** No step says "Build the friends page."

**Recommendation:** Add a new step (e.g., Phase 11.6) between Phase 10 (Hashtags) and Phase 11 (Introductions) to build the friends page. Or fold it into Phase 3 (Social Graph).

### 25. `REQUEST_HOLD_AFTER_PROFILE_CHANGE_HOURS` Appears in SPEC but Not in BUILD_PLAN
**SPEC.md §14:** This constant is new.
**BUILD_PLAN.md:** No step implements it. §8.1 mentions the cooldown but doesn't reference the constant name or the retired `BIO_CHANGE_COOLDOWN_HOURS`.

**Recommendation:** In BUILD_PLAN.md §8.1, add: "This step implements `REQUEST_HOLD_AFTER_PROFILE_CHANGE_HOURS` (spec value 12) on sending friend requests, not on changing the bio/photo. The old `BIO_CHANGE_COOLDOWN_HOURS` and `BIO_EDIT_GRACE_MINUTES` are retired."

### 26. The "Accessibility Overlay" Ban Is Mentioned in Three Places but Not Tested
**SPEC.md §16.4:** "No accessibility overlay widgets."
**ARCHITECTURE.md §3.8:** "Banned outright."
**BUILD_PLAN.md §16.2:** The "zero-foreign-requests check" tests for third-party scripts, but it doesn't specifically look for overlay widgets.

**Recommendation:** In BUILD_PLAN.md §16.2, add: "Also check for any `<script>` tags that load from a third-party accessibility overlay domain (e.g., accessibe.com, userway.org)."

### 27. The "No Counters" Rule Is Not Enforced in the Database Schema
**SPEC.md §17:** "No counts of any kind."
**ARCHITECTURE.md §4:** The schema has `rate_counters` (for rate limits) but no `post_count` or `follower_count`. Good.

But **SPEC.md §12.2** says "No unread-count badges." Yet the `notifications` table (ARCHITECTURE.md §4) has a `read` field. If you can query `WHERE read = false AND recipient = X`, you're computing an unread count. There's no architectural guard against this.

**Recommendation:** In ARCHITECTURE.md §4, add: "The model must not carry, and no query may compute, an unread badge count or a follower count"—this is already there. But also add a **database trigger or application-layer guard** that prevents queries that count unread notifications.

## Overall Assessment

This is an **exceptionally thorough** set of documents. The level of detail rivals a professional product specification. The founder clearly has a deep understanding of the domain and the technical stack.

**The biggest risks are:**

1. **Operational burden** (single point of failure for hashtag approvals, manual moderation, manual accessibility audits). The spec acknowledges these but doesn't fully solve them.

2. **Security assumptions** (Cloudflare proxy ban, email deliverability). These are defensible choices, but they're bold.

3. **Feature completeness vs. complexity** (editing hashtags and its privacy implications, the "friends page" that only arrived in v1.16). The scope is large for a solo builder.

4. **Accessibility testing** (manual only, no automated regression). This is the hardest part to maintain.

**The documents are internally consistent**—SPEC and ARCHITECTURE align, BUILD_PLAN follows from both. The few inconsistencies are minor (constants missing in BUILD_PLAN, missing step for the friends page) and easy to fix.

**My strongest recommendation:** Before starting Phase 2 (building code), do a **final pass through BUILD_PLAN** with a focus on:
1. Missing steps (like the friends page)
2. Missing constants (like `COMMENT_LENGTH_MAX`)
3. Security assumptions (like the Cloudflare proxy ban)
4. Accessibility test automation

Then build it. These documents are more than sufficient to start coding.
