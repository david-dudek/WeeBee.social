WeeBee mockups

Browser-viewable mockups of WeeBee as SPEC.md and ARCHITECTURE.md already describe it, built session by session so the founder can look at the platform before approving those documents. Each entry below names the SPEC section it renders. See mockups/NOTES.md for the running log of places the documents were silent, and mockups/CRIB.md for the shared constants, verbatim strings, and sample cast every session draws from.

M1 — The harness, and the feed

  • Feed — feed posts and profile-update notifications interleaved in reverse-chronological order, long-post folding, stated visibility, relative ages, the expiry countdown, an edited marker, an image post, and the dual-name display (SPEC §7.7, §7.5.1, §7.8, §7.9, §12.1–§12.3, §4.5.1).
  • Feed — older posts — the "← Newer posts" / "Older posts →" pagination pairing (SPEC §7.7.1).

M2 — The composer, and three single-post views

  • Post (composer) — the single composer for both post types: the required destination choice with no default and its error state, the feed audience picker and its over-30 warning, the blog hashtag picker and the live visibility line, the preformatted toggle and its explainer, the image alt-text prompt in both its states, a character-cap overrun, a rejected URL, the type-switch notices, and the "save as a group?" suggestion (SPEC §7.1, §7.2.1, §7.2.3, §7.3, §7.9, §11.2, §6).
  • A feed post — the only surface reactions ever render on: the reaction line on a post and on a comment, the react control in its "React" and "Reacted: …" states with the curated phrase list, comment folding, and no react control on David's own post or comment (SPEC §7.9, §8.1, §8.2, §8.2.1, §8.2.2).
  • A tagged profile post — the same view for a hashtag-gated profile post as seen by a friend-of-friend: the three-tag visibility line, the report action carrying its tag-mismatch reason, a commenter name rendered as plain text, and a reaction rendered as plain text (SPEC §7.9, §8.1, §8.2.2, §11.3).
  • A preformatted post — the platform's one documented reflow exemption: exact spacing, no soft-wrap, a keyboard-focusable named scroll container confined to the post's own box (SPEC §7.2.1, §16.3; ARCHITECTURE §3.8).

M3 — The profile, as a friend sees it

  • Profile — Blog tab — the persistent header (photo, display name mid name-change transition, report action) shared by all four tabs; the landing tab's post list, newest first, folded at BLOG_FOLD_CHARS; a feed post shown here as well as in its recipients' feeds; a pinned post in its chronological place; the normal-profile case of no pagination (SPEC §9.1, §4.5.1, §7.6, §7.7, §7.7.1, §7.9, §16.3).
  • Profile — Pinned tab — the author's curated shelf, folded at the tighter FEED_FOLD_CHARS; a pinned post's age shown under the ordinary relative-time rule with the "Pinned" marker standing in for the expiry countdown; a genuinely old pinned post reaching the long tail of the relative-age ladder; no trace of its expired older comments (SPEC §7.5, §7.5.1, §7.6).
  • Profile — Photos tab — the GALLERY_MAX = 8 image gallery as a <ul> of real, plain-tab-order <button>s with no caption field, the alternative text doing that job instead (SPEC §9.2, §9.4, §16.3).
  • Profile — About tab — the short bio (no clickable links, ever) and extended bio (friends only, allowlisted links permitted), profile hashtags linking to the not-yet-built discover page, and "the people you both know" rendered as names via the idiom's own "and others" form, never a count (SPEC §9.1, §9.4, §11.5).
  • Image overlay, from the gallery and image overlay, from a post — the click-to-expand modal dialog of §7.2.2 rendered open, with the dimmed page behind it and the obligations a real click would add (focus in, trapped, Escape out, focus restored) stated in page text; the gallery variant alone carries Previous/Next controls (SPEC §7.2.2, §9.4, §16.3).

M4 — Non-friend profile views, discover, friends, preview-as

  • Profile — a plain friend-of-friend's view — the basic tier only, header plus About, and nothing else: no tab strip at all, since a lone qualifying tab draws none; the unconditional "you and David are not friends" line below the content, never above it; no gallery, no extended bio, and no placeholder marking either absence (SPEC §9.1, §9.2).
  • Profile — a hashtag-matched friend-of-friend's view — basic tier plus the one profile post that carries a shared hashtag, filtered with no placeholder for what doesn't match; a two-tab strip (About, Blog) with Pinned itself omitted because nothing pinned matches; comments visible with a commenter's name rendering as plain text where this viewer has no connection to them (SPEC §9.2, §11.3, §8.1).
  • Discover and Discover, filtered to a tag — the one dedicated, pull-only discovery surface: friend-of-friend people suggestions with auto-context, hashtag-gated matched posts, and the viewer-scoped tag filter reached by clicking a tag anywhere; no counts, no global tag browsing, and nothing pushed to the feed or announced to anyone (SPEC §11.2, §11.3, §11.4).
  • Friends — the user's own friend list, alphabetical by display name and no other order, with a filter box carrying the required visible label "Filter your friends"; no friend count anywhere on the page (SPEC §11.6, §17).
  • Preview-as — a specific friend, a generic friend-of-friend, a friend-of-friend carrying a chosen hashtag, and the friend-request card — all four required preview-as modes, each marked with a persistent real-text banner and an "Exit preview" link; the per-friend contact-card cascade; the deliberately absent "as a specific friend-of-friend" mode, explained rather than built; and the frozen-versus-live field split on the request card, stated field by field (SPEC §9.5, §10.3, §5.2).

M5 — Friendship and contact flows

  • A friend request, received — the request card as its recipient sees it, with §9.1's frozen/live field split labelled field by field, the report action, and silent accept/decline controls (SPEC §5.2, §9.1, §13.2).
  • Friend requests you've sent — the sender's side: a pending request with no invented countdown, the honest "you can send friend requests again in N hours" message after a profile change, and the friend-cap error on either side of a request (SPEC §5.1, §5.2, §13.6).
  • Introduce two friends and Alice asks you to introduce her to Henry — both free-text-free introduction flows: the broker-initiated picker and its per-candidate card, an incomplete introduction that never names who declined, the requested flow's silent decline, and what happens if you agree (SPEC §5.5, §11.1, §11.3).
  • Your contact card — the owner's own card: the empty starting state, adding an item, and the full three-level visibility cascade — default, group override, individual override — as real, keyboard-operable checkboxes, including a worked deny-beats-allow conflict between two groups (SPEC §10.1, §10.2, §10.3; ARCHITECTURE §3.8).
  • Requesting a contact card — the picker-based request and its auto-reply, both a populated case and the real empty state, plus §10.5's request-more-access flags, clearly labelled "may ship in v1.1" (SPEC §10.4, §10.5).
  • Unfriend or block Sofia — the unfriend confirmation using §5.3's wording verbatim, and the block action's fully mutually invisible effects stated in full alongside it (SPEC §5.3, §5.4).
