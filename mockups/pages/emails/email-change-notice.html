SPEC §4.6: "a notice is sent to the old address" once an email change completes — this is that notice, carrying no code and no link, unlike email-change-code.html, which goes to the new address. §4.6.1 names "email change" among the three security-event types that "carry absolute timestamps wherever they appear," alongside new-device login and password change — the absolute time above follows from that, using the same example timestamp §12.3 itself gives. Interpretive note: this session's own "before you finish" checklist says absolute times appear "only in security-event and inactivity-deletion," which would seem to exclude this file by name — but §4.6.1's own text plainly includes email change among the events this rule governs, and the standing rule for this whole track is that SPEC leads. This tension is recorded in mockups/NOTES.md rather than silently picked one way. The checkable promise above is reused verbatim from §4.6.1, since this is exactly the moment a recipient might worry "was that me?" and be most vulnerable to a look-alike follow-up email.
