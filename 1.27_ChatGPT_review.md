**NOTE: This review only included SPEC.md, ARCITECTURE.md, and README.md** 

Yes. I reviewed all three documents as a system rather than treating them independently. My overall conclusion is:

> **WeeBee is technically buildable as a small, private web application, and the core architecture is sensible. But the documents are not yet at the level where I would confidently hand them to an AI coding agent and expect the resulting system to satisfy the promises.**
>
> The biggest risks aren't Django, PostgreSQL, or the basic web application. They are **permission semantics, privacy/security claims, operational assumptions, moderation, the strength of some "no reach" claims, and several places where the documents have become so elaborate that the specification itself is becoming a source of complexity.**

I'd currently put the likelihood roughly at:

| Goal                                                                                              |                             My assessment |
| ------------------------------------------------------------------------------------------------- | ----------------------------------------: |
| Working prototype for founder + ~20 friends                                                       |                                  **90%+** |
| Reliable small private network, ~100 users                                                        |                                **80–90%** |
| Well-engineered network at ~500 users                                                             |                                **65–80%** |
| "Build exactly from these documents with an AI and little human intervention"                     |                                **50–65%** |
| Scaling the described architecture to hundreds of thousands/millions without substantial redesign |                        **Low / unproven** |
| Literal fulfillment of every privacy/accessibility/security promise as currently worded           | **Moderate, but not yet safe to promise** |

The encouraging part is that **most of the problems are fixable without changing the basic product concept.**

# 1. The biggest problem: the specification is becoming too complicated

This is the overarching issue.

The project began with a beautifully simple idea:

> invite-only + bounded friendships + no reposting + no algorithmic feed + private audiences + expiring content.

But SPEC is now 1,159 lines, and ARCHITECTURE is 860 lines. There are elaborate rules for:

* two kinds of posts
* audience snapshots
* live friendship checks
* FoF hashtag gates
* profile tiers
* pinned posts
* expiring reactions
* comment-specific visibility
* per-item contact-card permissions
* group overrides
* individual overrides
* name transitions
* friend-request snapshots
* profile-photo abuse controls
* moderation snapshots
* ban/deactivation semantics
* notification coalescing
* timestamp ladders
* accessibility partials
* accessibility audits
* theme inheritance
* viewer theme overrides
* URL allowlists
* invite trees
* inactivity deletion
* backup deletion windows
* etc.

The documents themselves acknowledge that complexity is accumulating. For example, ARCHITECTURE explicitly says the visibility system is the hardest feature and requires a central engine precisely because otherwise rules will diverge. 

That's a good architectural response—but it doesn't eliminate the underlying complexity.

### My concern

You are building a social network whose primary selling point is **simplicity and resistance to manipulation**, but the implementation specification is becoming a fairly sophisticated policy engine.

That isn't necessarily wrong. But it changes the project from:

> "Build a simple private social network."

into:

> "Build a privacy-sensitive access-control system with a social-network UI."

That's a considerably harder project.

**Recommendation:** Before coding, classify every rule into:

1. **Core security invariant**
2. **Core product behavior**
3. **Nice-to-have**
4. **Implementation detail**

Then aggressively remove category 3 from v1.

# 2. SPEC §2 has an actual unresolved contradiction involving public pages

This is one of the clearest issues.

SPEC §2 says:

> "No public (logged-out) pages except login/registration/invite-acceptance."

Yet the documents now require an accessibility statement and privacy/terms material, and ARCHITECTURE itself admits that the built system will have additional public pages.

ARCHITECTURE §15's resolution record explicitly acknowledges this unresolved problem:

> "SPEC §2's list is in fact narrower than the built system in a second way ... the privacy policy and accessibility statement are linked from login..." 

So this isn't merely something I inferred—the architecture document knows there's a mismatch.

### Why it matters

An AI developer following SPEC literally might reject `/privacy`, `/terms`, and `/accessibility` because they violate §2.

Another AI might create them because ARCHITECTURE/build-plan tells it to.

That's exactly the sort of ambiguity your "authoritative document" philosophy is supposed to eliminate.

### Severity

**Medium.**

### Fix

Change SPEC §2 to explicitly enumerate the legal/accessibility pages, e.g.:

* login
* registration
* invite acceptance
* privacy policy
* terms
* accessibility statement
* health endpoint, if desired

Or define "public page" more narrowly.

# 3. "GDPR-compatible" is much too strong a claim

**SPEC §15.1** says:

> "GDPR-compatible by design (minimal collection, guaranteed erasure and expiry, export, no profiling)." 

This is one of the places I'd strongly change the wording.

Minimal collection, deletion and export are **good GDPR design characteristics**, but they do not establish GDPR compliance.

For example, the documents still need to deal with things such as:

* lawful basis for processing
* controller/processor relationships
* email provider processing
* international data transfers
* data-processing agreements
* privacy notices
* retention of security logs
* legal basis for moderation records
* handling rights requests
* identity verification for rights requests
* breach notification procedures
* potentially legitimate-interest balancing
* operator access
* data concerning other people contained in exports
* legal retention exceptions
* backup restoration implications

The email provider is explicitly acknowledged as seeing email addresses and email contents. 

### Particularly important

Your export promise says:

> "Every user can download a complete ... copy of their data."

But "complete" is potentially problematic because the system contains information about relationships with other users.

For example:

* friendship records
* mutual-friend relationships
* contact-card permissions
* moderation records
* invite ancestry

You need to define precisely **whose data the export contains and whose data it deliberately excludes**.

### Recommendation

Replace "GDPR-compatible by design" with something like:

> "Designed with GDPR principles in mind; legal compliance depends on implementation, jurisdiction, contracts and operating practices."

Then have the lawyer review the actual system and privacy documentation.

# 4. The deletion promise is better than it used to be—but still has an important technical trap

This part has improved substantially.

The documents correctly acknowledge that backups mean deletion isn't instantaneous in the literal physical sense. ARCHITECTURE says deleted material can remain in encrypted backups for up to 30 days. 

That's good engineering honesty.

However, the specification says:

> "deleted content ... purged from the last encrypted backup within 30 days"

while the architecture says backups are **nightly**.

The actual deletion time therefore depends on the backup schedule and retention implementation.

The wording avoids the "exactly day 120" trap, which is good.

### Bigger problem

You need to think about **backup restoration**.

Suppose:

1. User deletes their account.
2. Their content disappears from production.
3. A disaster happens.
4. You restore a backup that contains their deleted data.

What happens?

The documents say backups are never used to restore an individual account, but the system's disaster recovery process can restore an entire database.

That creates a potentially nasty privacy issue:

> A disaster recovery procedure could resurrect data that the live system had already deleted.

The documents don't appear to fully specify the mechanism that prevents this.

### Severity

**High for the deletion guarantee.**

### Fix

Define a **deletion ledger/tombstone mechanism** or equivalent restoration rule.

For example:

* deletion records survive backup restoration long enough to prevent resurrection
* restore process replays deletion tombstones
* or backup retention is treated as immutable historical snapshots and a restore must apply a post-backup deletion ledger

This is especially important if "guaranteed erasure" remains a formal promise.

# 5. The "one server" architecture is appropriate—but the backup story isn't as simple as the documents imply

The core architecture is reasonable:

> Caddy → Django → PostgreSQL + private filesystem

For this project, that's a good choice. The architecture correctly recognizes that image authorization is a major privacy concern. 

But several statements are overly confident.

ARCHITECTURE says:

> "If the VPS dies, a new one is: install Docker, copy the project, restore backup, docker compose up." 

That's a **runbook aspiration**, not necessarily a realistic disaster recovery procedure.

A real recovery also involves:

* DNS
* certificates
* secrets
* backup credentials
* backup encryption key
* Docker images/dependencies
* database version compatibility
* filesystem permissions
* image files
* media integrity
* cron configuration
* Caddy configuration
* email-provider credentials
* domain authentication
* potentially DNS propagation
* application version corresponding to database schema

The documents recognize several of these, which is good, but the sentence "that's the entire disaster-recovery runbook" is too confident.

### Severity

**Medium.**

# 6. A single VPS is vulnerable to one particularly bad failure: the disk

The architecture actually does a good job identifying this.

It estimates:

> 500 users ≈ 50 GB

and says disk, rather than CPU or PostgreSQL, becomes the first constraint. 

That's a useful observation.

However, there is a subtle problem in the calculation.

The architecture assumes approximately **3 MB per stored image** after processing. That's a reasonable planning estimate, but not a guarantee.

Actual storage depends heavily on:

* image content
* JPEG/PNG/WebP encoding
* compression settings
* dimensions
* whether multiple derivatives are stored
* PNG screenshots
* animated formats, if permitted
* thumbnails
* temporary upload files
* orphaned files
* filesystem overhead

More importantly, **"permanent ceiling of ~19 images" isn't actually a permanent storage ceiling if replacement semantics retain old images temporarily, backups exist, or deletion cleanup fails.**

The system needs an explicit storage invariant:

> For every account/content deletion operation, all production copies and derivatives are either deleted synchronously or placed on a bounded cleanup queue.

Otherwise disk growth can exceed the mathematical model.

# 7. The scaling claims are too optimistic

This is probably the biggest architectural overstatement.

ARCHITECTURE says:

> "Stage 1 — a bigger single server (tens of thousands of users)"
> "Stage 2 — ... hundreds of thousands"
> "Stage 3 — millions." 

I would **not** make those claims in the design document.

The architecture might eventually scale surprisingly far, but the documents don't establish that it will.

The problematic sentence is:

> "A million users here is closer to 'a million small mailboxes' than 'one giant town square,' and mailboxes scale easily." 

That's an appealing analogy, but it isn't an engineering proof.

### Why

The expensive parts aren't just posts.

You have:

* friendship graph queries
* mutual-friend queries
* FoF discovery
* hashtag matching
* visibility checks
* notification generation
* notification permission re-checking
* image authorization
* moderation
* invite-tree relationships
* account deletion
* background expiration
* backup generation
* backup verification
* email delivery
* potentially very active users with 300 friends
* hundreds of posts over 90 days
* large amounts of private image traffic

And the "no query ever spans the whole network" assertion isn't universally true in the conceptual sense. The discover system can perform graph traversal across a user's social neighborhood, and operator/forensic functions may naturally need broader queries.

### More importantly

**PostgreSQL sharding is not a trivial "next stage."**

Friendships cross users. A friendship between shard A and shard B becomes a cross-shard relationship. Mutual-friend calculations can become cross-shard operations. Discovery can become cross-shard. Account deletion becomes cross-shard.

So:

> "sharding is where most social networks suffer ... this design shards about as gracefully as a social network can"

is an unsupported conclusion.

It may be true. But you don't know yet.

### Recommendation

Replace the million-user discussion with:

> "The architecture is intentionally designed so that the first scaling steps can probably be evolutionary rather than a rewrite. Actual capacity and scaling boundaries must be established through load testing before making quantitative claims."

That's much stronger engineering writing.

# 8. Read replicas create a subtle security problem that isn't addressed

The scaling plan proposes PostgreSQL read replicas. 

But your permission model is **security-sensitive and state-sensitive**.

Imagine:

1. Alice blocks Bob.
2. The block is committed to the primary database.
3. A read hits a replica before replication catches up.
4. Visibility code asks whether Bob can see something.
5. Replica says the block doesn't exist yet.
6. Bob sees something he shouldn't.

This isn't merely a performance issue.

The same applies to:

* friendships
* account deletion
* bans
* profile changes
* audience changes
* contact-card permissions
* hashtag gates

### Therefore

At scale, the architecture must specify which reads are permitted from replicas.

Likely:

> **Authorization-critical reads must use sufficiently current/strongly consistent state.**

You can't simply say "Postgres read replicas" and assume they're interchangeable.

This is a **high-severity architectural omission** if the scaling section is intended to be prescriptive.

# 9. The visibility engine is a good idea—but it is also the project's biggest failure point

I strongly agree with the central visibility engine.

ARCHITECTURE explicitly requires:

* `can_see_post`
* `can_see_comment`
* `can_see_profile_tier`
* `visible_contact_card`
* `are_connected`
* `can_act` 

This is exactly the right instinct.

But there's a danger in the statement:

> "everything else must ask it."

The engine can become a **god object**.

It is being asked to understand:

* friendships
* blocks
* FoFs
* post audiences
* hashtag gates
* profile tiers
* comments
* reactions
* contact cards
* introductions
* requests
* actions
* potentially notifications

That can become extremely difficult to reason about.

### Better approach

Make the engine a **small, explicitly modeled policy layer**, with lower-level primitives beneath it:

```text
relationship service
block service
audience service
profile visibility service
content visibility service
contact-card policy
action authorization
```

Then `visibility.py` can compose them without becoming 3,000 lines of conditional logic.

The current design is good conceptually but needs a structural constraint such as:

> "No visibility function may perform unrelated state mutation, notification creation, or business workflow."

# 10. The comment visibility correction is a warning sign

You actually found a real contradiction yourself in v1.26.

The architecture now says that a comment's audience differs from the post's because blocks can hide a comment while leaving the post visible. 

That's a legitimate rule.

But it illustrates a deeper problem:

**Your specification is now complicated enough that seemingly obvious relationships are no longer safe assumptions.**

For example:

> "If I can see the post, I can see its comments."

Sounds natural.

But isn't true.

The same thing will happen elsewhere.

### I would introduce a formal concept:

**Visibility must always be an explicit function of `(viewer, object)` rather than inherited by assumption.**

That principle should be elevated into the architecture.

# 11. The "no reach" claim is carefully qualified—but some of the supporting reasoning is not convincing

The strongest version of the claim is actually reasonable:

> No mechanical propagation beyond the author's selected audience.

The documents explicitly admit that someone can copy/retype content and that this isn't prevented. 

That's intellectually honest.

But this claim is much weaker:

> "A bounded graph has no long tail of weak ties."

That's not generally true.

A graph with maximum degree 300 can absolutely have:

* long paths
* communities
* bridges
* highly connected hubs
* weak ties
* small-world behavior

The degree bound constrains fan-out, but doesn't eliminate long-distance connectivity.

### More importantly

Hashtag-gated discovery explicitly creates a mechanism for content to cross friend boundaries.

A post can be:

> Author → friend → FoF sharing hashtag

and the FoF can then become a friend, creating another connection through which other material becomes visible.

That's not a flaw. It's literally part of the product.

But it means the more accurate philosophy is:

> **"No algorithmic or mechanical viral propagation."**

not:

> **"Nothing can travel beyond the author's chosen audience."**

Your §1.2 qualification largely gets you there, but I'd standardize the terminology around **mechanical propagation** throughout the documents.

# 12. The hashtag system is simultaneously a discovery system and an audience-control system

This is clever, but creates an unexpected privacy property.

SPEC §11.3 says a profile post with multiple hashtags is visible to a FoF if **any one** matches. 

Therefore:

> Adding another hashtag increases the audience.

That's explicitly acknowledged.

But it means the hashtag picker is effectively an **audience-expansion control**, not merely metadata.

That creates a UX/security requirement:

### Editing hashtags is equivalent to changing the audience.

You partially address this with stated visibility and notifications to commenters.

But I'd make this much more explicit:

> **A hashtag edit on a profile post is an audience change and must be treated with the same security rigor as changing a feed-post audience.**

Especially test:

* adding a tag
* removing a tag
* adding a tag after comments exist
* removing a tag after comments exist
* viewer adding/removing their own profile tag
* friendship changing simultaneously
* blocking/unblocking
* post pinning/unpinning

This is one of the areas I'd heavily fuzz-test.

The request card contains:

* name
* mutual friends
* hashtags

# 15. The invite system doesn't actually establish that users are "vouched"

SPEC §1.3 says:

> "Every account enters through a personal invitation from an existing member. There are no strangers; every user is at most one trusted hop from someone who vouched for them."

But the invitation mechanism only proves:

> **someone possessing an invite chose to send it.**

It does not prove the inviter actually knows the recipient or trusts them.

That's a semantic overstatement.

Someone could:

* post an invitation link elsewhere
* give it to a stranger
* sell it
* publish it
* send it to a large mailing list

Even with one-time invitations.

### The architecture doesn't eliminate this.

The invite tree provides traceability, not trust.

### Better language

> "Every account enters through an invitation from an existing member. The invite graph provides social accountability."

That's true.

"Vouched" implies something stronger.

# 16. The invite tree itself creates a permanent privacy record

SPEC §4.3 says the invite tree survives deletion as anonymized structural data.

That's reasonable for abuse analysis.

But there is an important privacy question:

> Can the operator reconstruct social relationships from the invite tree indefinitely?

Yes.

Even if names/emails disappear, the graph survives.

This is especially relevant because the philosophy says:

> "Data minimalism."

You need to explicitly classify the invite tree as **long-term personal data / pseudonymous relational data**, not as harmless anonymous metadata.

The current wording risks understating its privacy significance.

# 17. The moderation system is too weak for the promise the project makes

The documents have a sensible basic report mechanism:

> report → frozen copy → human review → delete/warn/ban.

That's good.

But formal policies and appeals are deferred. 

That's fine for a tiny prototype.

It's **not fine for a public service**.

The biggest problem isn't lack of sophisticated moderation.

It's this:

> **There is only one operator.**

The specification explicitly accepts the operator as a single point of failure in hashtag curation. The same is true of moderation.

If the operator is:

* asleep
* sick
* traveling
* unavailable
* overwhelmed
* the subject of the report

then moderation stops.

For the founder's 20-person prototype: fine.

For "public later": no.

The documents should clearly state:

> **Single-operator moderation is a prototype constraint and is not a viable public-scale safety model.**

# 22. The anti-phishing claims are mostly good, but one claim is too absolute

The "codes rather than login links" strategy is excellent.

But the claim that it makes a fake login email:

> "self-evidently fake"

is too strong.

An attacker can send:

> "Your WeeBee account has been compromised. Go to weebee-login-security.example..."

and tell the victim to visit a fake site manually.

The code/no-link policy reduces phishing risk, but does not make phishing self-evidently fake.

Similarly, password managers don't necessarily prevent every social-engineering attack.

### Better claim

> "The policy substantially reduces the credibility of fake login/reset emails that ask the user to click a login link."

That's defensible.

# 23. The "passkeys capability now, feature later" idea is unnecessary complexity

ARCHITECTURE creates a credential model capable of passkeys before passkeys exist. 

This isn't terrible, but it violates one of the project's own strongest principles:

> Keep the system small.

Passkeys later are not necessarily a schema migration disaster.

You could add them later with:

* a credential table
* WebAuthn credentials
* recovery workflow

The current approach is reasonable, but I'd ask:

> Is this actually saving enough future work to justify introducing credential polymorphism now?

For a solo AI-built project, **every unused abstraction is another thing the AI can misunderstand.**

Every feature interacts with expiration.

You have:

* posts
* comments
* reactions
* pinned posts
* notifications
* reported posts
* moderation freezes
* deleted accounts
* banned accounts
* backups
* friend-request snapshots

# 32. Cron is reasonable—but cron isn't transactional

ARCHITECTURE §2 Decision 5 chooses cron instead of Celery/Redis. That's perfectly reasonable for this scale.

The problem isn't cron.

It's that several jobs perform destructive operations:

* delete content
* delete accounts
* purge moderation copies
* expire notifications
* process backups

You need every job to be:

* idempotent
* restartable
* safe if interrupted
* safe if run twice
* safe if two instances accidentally run concurrently

For example:

> What if `expire_content` starts deleting 10,000 images and the container dies halfway through?

The next run should safely continue.

This should be a formal job invariant.

---

# 33. The backup verification job has a dangerous interaction with the single server

The architecture wisely says `verify_restore` checks disk capacity first. 

But restoring a production-sized database on the production VPS is still operationally risky.

At some point:

> production database + production images + backup + temporary restored DB

can consume enormous disk and I/O.

At 500 users, perhaps manageable.

At larger scale, it isn't.

So the architecture's scaling plan needs to explicitly move backup verification off the production host earlier than the current text suggests.

---

# 34. The uptime strategy is acceptable for the prototype, but not for launch

This is actually one place where I agree with the documents' self-awareness.

ARCHITECTURE explicitly admits:

> `check_health` cannot report its own death. 

That's exactly right.

For 20 friends, relying on people noticing is reasonable.

For public launch, it isn't.

The document correctly says external monitoring should happen before public phase.

I would simply elevate that from:

> "deferred with intent"

to:

> **hard launch gate.**

---

# 35. The cost estimates are plausible for the prototype, but shouldn't be treated as total operating cost

The architecture estimates roughly:

> $10–35/month. 

That's plausible for a tiny deployment.

But it excludes meaningful human costs:

* accessibility tester
* lawyer
* domain/DNS
* backup expansion
* operator time
* moderation time
* email volume
* incident recovery
* monitoring
* eventual image storage

The documents do acknowledge some of these elsewhere.

I'd call this:

> **infrastructure cash cost**

rather than:

> total project cost.

---

# 36. "One server" doesn't necessarily mean "privacy sovereignty"

The architecture says the VPS is effectively a landlord rather than a roommate.

That's a useful analogy, but the text sometimes treats VPS hosting as if it means complete custody of the data.

A VPS provider can potentially have access to:

* host storage
* snapshots
* backups if configured through provider services
* metadata
* network infrastructure

The encryption-at-rest story helps, but the provider still isn't equivalent to owning physical hardware.

Again, this isn't a reason not to use a VPS.

Just don't oversell the privacy guarantee.

---

# 37. The "no public content" model creates a discoverability problem that is intentionally accepted—but may undermine the second mission

The mission has two goals:

1. maintain existing relationships
2. form new friendships through mutual friends/shared interests

The first works naturally.

The second depends heavily on:

* hashtags
* FoF discovery
* operator-curated vocabulary

The architecture admits the vocabulary operator is a single point of failure. 

This creates an interesting product risk:

> The more private and bounded the system becomes, the more important the discovery mechanism becomes—but the discovery mechanism is the most complex and operator-dependent part.

That's not a technical contradiction, but it's a product risk I'd explicitly track.

---

# 38. The "friendship is symmetric" rule creates awkward edge cases around blocking

You have:

> friendship symmetric

but:

> block is asymmetric in initiation and symmetric in effect.

That's reasonable.

However, you need to be extremely careful about:

* A blocks B.
* A unblocks B.
* B has meanwhile changed profile.
* B sent a request before being blocked.
* B was in a group.
* B had contact-card permissions.
* B had comments/reactions.
* B followed a post.
* B was mentioned in a notification.
* A and B later become FoFs again.

The documents cover many of these individually, but I don't see evidence of a formal **state-transition model** tying them together.

I'd make one.

---

# 39. The notification system is more sophisticated than the philosophy suggests

You say:

> "The feed is a mailbox, not a machine."

Good.

But then you have:

* comment notifications
* reaction notifications
* profile notifications
* coalescing
* following
* optional email
* profile-post audience expansion notifications
* moderation emails
* security emails
* inactivity emails

This is increasingly an engagement system.

The architecture acknowledges the risk. SPEC §12.4 explicitly says comment notifications are the first link in an engagement loop. 

I think this deserves an explicit product invariant:

> **Notifications may communicate an event that requires social response, but may never manufacture urgency.**

Then test every future notification against that.

---

# 40. There is a particularly interesting tension between "no behavioral inference" and the follow system

SPEC says:

> "The platform never infers. Users state their intent."

Then commenting automatically turns following on.

The document explicitly defends this by saying commenting is treated as stated interest rather than inference. 

I think that's philosophically defensible—but borderline.

The user didn't explicitly say:

> "Notify me about future comments."

They commented.

The system infers that this action means they want updates.

You can call that a product rule rather than behavioral inference, but it would be cleaner to have:

> "Commenting defaults to following, but the user is explicitly informed and can disable it."

That makes the consent more obvious.

---

# 41. Some language is stronger than the implementation actually guarantees

I would search the entire project for words like:

* **never**
* **guaranteed**
* **nothing**
* **always**
* **exactly**
* **complete**
* **fully**
* **permanent**
* **absolute**
* **impossible**

There are many.

Examples include:

> "Nothing can go viral."

> "guaranteed erasure"

> "full erasure"

> "never"

> "exactly"

These aren't necessarily wrong because the document often qualifies them.

But every absolute statement creates a test obligation.

For an AI-generated implementation, absolute language is dangerous.

I'd introduce a rule:

> **Every absolute user-facing guarantee must have a corresponding automated test or explicitly documented operational dependency.**

# 42. README has a subtle problem: it says these are "complete design documents," but BUILD_PLAN.md isn't among the supplied documents

README says:

> "This repository holds its complete design documents."

Then it describes BUILD_PLAN.md as a downstream document that hasn't yet been produced. 

That's a minor wording problem, but important given your stated goal that the documents should be executable.

Currently they are **not sufficient to build the system exactly as described**, because several implementation decisions are explicitly deferred to BUILD_PLAN.

For example:

* email provider
* VPS
* backup target
* exact build sequence
* exact founder operations
* accessibility testing scheduling

So I would change:

> "complete design documents"

to:

> "current design documents; implementation/build documents follow."

# 43. The claim that Django gives you "login/password reset with correct security" is too broad

ARCHITECTURE says Django provides:

> "Login/logout/password reset with correct security." 

Django provides excellent primitives and secure defaults.

But your authentication design is **not Django's default authentication flow**.

You have:

* numeric recovery codes
* email change codes
* special invitation behavior
* breach-password checking
* custom lockout
* per-account and per-IP throttling
* credential table
* future passkeys
* special banned-account login
* security-event emails

So the application is implementing a substantial custom authentication layer.

The accurate statement is:

> "Django provides secure primitives and defaults on which the custom authentication requirements are built."

That's a meaningful distinction.

---

# 44. "DMs are solved" is a product assumption, not a technical fact

SPEC §10 says person-to-person communication is already solved by email/messengers.

That's philosophically coherent, but the actual user experience may suffer.

For example:

> "I just met someone through WeeBee. I want to say hello."

The system requires:

1. friendship
2. contact-card exchange
3. external application

That's a deliberate product choice.

Not a flaw, because you've explicitly decided it.

But I would remove language like:

> "this is a solved problem"

and say:

> "We deliberately delegate person-to-person messaging to external channels."

That avoids presenting a subjective product decision as an objective technical fact.

---

# 45. The "no API" + export system deserves more thought

You promise complete JSON export.

That's effectively a **data interchange interface**, even though it isn't an API.

That's fine.

But the export itself needs:

* schema version
* stable identifiers
* relationship representation
* deleted-account representation
* timestamps
* media filenames
* MIME types
* character encoding
* future compatibility

Otherwise "open format" isn't enough to ensure credible exit.

---

# 46. The export can itself become a privacy leak

Suppose Alice exports her data.

Does the export include:

* Bob's email address from Alice's contact card?
* Bob's phone number?
* mutual friend names?
* invite-tree information?
* notification actor names?
* moderation information?
* comments by other users on Alice's posts?

The current export description says:

> profile, posts, comments they authored, friend list, groups, contact card, images. 

That's relatively narrow, which is good.

But "complete copy of their data" should be changed to something like:

> "Complete export of the user's exportable account data, excluding other users' personal data."

Then define it formally.

---

# 47. There is a significant "AI coding model" risk

The project is explicitly designed for AI-assisted construction.

README says the documents are written so that AI models can execute them. 

I think this is the **largest practical risk to successful implementation**.

Not because AI can't write Django.

It can.

The problem is that your system contains **interacting invariants**.

A model can correctly implement:

> "comments disappear when blocked"

and incorrectly implement:

> "comments are visible to everyone who can see the post."

Both are individually reasonable interpretations.

You already discovered exactly this class of problem in v1.26.

### Therefore

The project needs something stronger than prose.

You need **machine-checkable invariants**.

For example:

```text
INVARIANT: A viewer can never receive a rendered object unless
can_see(viewer, object) is true.

INVARIANT: Every image response is permission checked.

INVARIANT: Blocking A→B means neither A nor B can observe
the other's existence through any user-facing surface.

INVARIANT: Expired content cannot be returned by any application query.
```

These become tests.

# 48. I would add property-based/security testing

This project is unusually well suited to it.

Generate random:

* users
* friendships
* blocks
* groups
* hashtags
* posts
* audiences

Then assert invariants.

For example:

> If A blocks B, there must be no route through which B can discover A.

You can generate hundreds/thousands of random graphs and test the visibility engine.

This is far more powerful than manually testing every page.

# 50. The operator is a major trust boundary

The documents spend enormous effort preventing users from seeing things they shouldn't.

But the operator has extremely broad power.

Django admin can potentially access:

* user data
* contact information
* reports
* moderation records
* images
* relationships
* email addresses

The project philosophy emphasizes user privacy, but operator access deserves an explicit policy.

Questions:

* Can the operator view contact cards?
* Can the operator read user posts?
* Can the operator see private groups?
* Is operator access logged?
* Can the operator export everyone?
* Are admin actions audited?
* Is there one operator account or several?
* Is MFA required for admin?
* Is admin exposed at a predictable URL?
* Can the admin be accessed from the public internet?

This is a major omission compared with how much attention is given to user-to-user permissions.

# 51. The Django admin should absolutely not be treated as "free"

ARCHITECTURE repeatedly calls Django admin the free operator console.

It's free in **software licensing**, but not free in engineering/security.

You still have to:

* configure admin permissions
* restrict models
* prevent dangerous bulk actions
* audit access
* secure admin authentication
* disable unnecessary models
* handle CSRF
* consider admin enumeration
* protect the URL
* possibly require MFA
* ensure sensitive fields aren't unnecessarily visible

You already identified the bulk-ban problem. That's evidence that admin's generic capabilities can actively conflict with product policy. 

So I'd say:

> "Django admin supplies the foundation for the operator console."

rather than:

> "operator console for free."

# 52. One especially important omission: database constraints

The architecture talks about PostgreSQL's integrity guarantees, which is good. 

But the specification should explicitly say which invariants are enforced at the database layer.

Examples:

* one friendship per pair
* one reaction per user/object
* maximum group size
* unique active login email
* invite redemption exactly once
* no self-friendship
* no self-block
* post audience max
* comment ownership
* etc.

Some constraints cannot be enforced purely with ordinary DB constraints, but some absolutely can.

This is an important defense against AI coding errors.

# 53. Some "raise-only" configuration rules are questionable

SPEC §1.3 says:

That's philosophically interesting.

For example:

* content TTL
* name-change cooldown

* notification window
* request hold

If you later discover that 90-day content retention is a privacy problem, "never lower" could prevent a responsible correction.

The document distinguishes caps from mechanisms in places, but the broad language is too strong.

* friend count
* group size
* audience size
* gallery count

Not every temporal constant.

# 62. My biggest recommendation

**Do not start by building the UI.**

The project's first code should probably be a **policy/authorization test harness**, not a social network.

Build:

```text
User
Friendship
Block
Group
Post
Audience
Hashtag
Comment
Reaction
Profile
```

Then build the visibility engine and write hundreds/thousands of tests against it.

For example:

```text
Alice is friends with Bob.
Bob is friends with Carol.
Alice posts to Bob.
Carol cannot see it.

Alice posts to Bob and Carol.
Bob blocks Carol.
Carol can see Alice's post.
Carol cannot see Bob's comment.

Alice posts #hiking.
Bob is Alice's FoF and has #hiking.
Bob can see it.

Bob removes #hiking.
Bob cannot see it.

Alice blocks Bob.
Bob cannot discover Alice through:
  profile
  friends
  mutual friends
  hashtag
  comments
  reactions
  notifications
  introductions
  requests
```

Once that engine is trustworthy, the HTML is comparatively easy.

# Bottom line

**I do not see a fundamental "this can't be built" flaw.** The proposed Django/PostgreSQL/one-VPS architecture is entirely reasonable for the initial target, and I actually think the architectural instinct—particularly server-side rendering, permission checks on the server, private image serving, centralized visibility logic, limited dependencies, and explicit expiration—is quite good. 

The main danger is different:

> **The project has evolved from a simple social-network concept into a fairly intricate privacy/access-control system, while the documentation still sometimes talks about it as though it were simple.**

The **prototype is highly feasible**.

The **500-user system is feasible with careful engineering**.

The **"public later" / hundreds-of-thousands / millions story is currently an architectural hypothesis, not something established by the design**. The scaling section should be rewritten as a set of possible evolutionary paths rather than confident capacity claims. 

And most importantly, before letting an AI coding agent build this, I'd add three things:

1. **Authorization matrix**
2. **Threat model**
3. **Machine-testable invariants/state-transition suite**

Those three artifacts would address the biggest weakness I've found: **the prose is exceptionally detailed, but detailed prose is not the same thing as an unambiguous executable specification.**
