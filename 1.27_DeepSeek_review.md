# WeeBee Design Documents: Comprehensive Review

## Executive Summary

This is an exceptionally well-structured, thoughtful, and *self-aware* design for a small-scale private social network. The documents demonstrate remarkable discipline: they acknowledge their own limitations, record rejected alternatives, maintain a clear version history, and explicitly flag open questions. The architectural choices are conservative, defensible, and appropriate for a solo founder building with AI assistance.

**However, there are significant problems—not fatal ones, but real ones that will bite during implementation if not addressed.** The most serious issues cluster around:

1. **Over-reliance on the "operator" for ongoing curation** (vocabulary, URL allowlist, reaction set, themes, contact moderation)—these are not one-time setup tasks but *continuous* burdens that will burn out a solo founder.
2. **The visibility engine's correctness depends on humans never making mistakes**—one bypass, one "quick fix" that inlines a permission check, and the privacy model is silently broken.
3. **Accessibility conformance is specified in excruciating detail but depends on a single tester at launch**—and the "continuous" tests catch only mechanical issues, not the real usability problems.
4. **The 90-day deletion promise has a 30-day backup window, and users will not understand this distinction**—the documents are honest about it, but the user-facing communication will inevitably simplify to "everything is deleted."
5. **The moderator queue and operator workflows are acknowledged as "deferred" but are actually essential**—without them, the platform cannot function if even one bad actor appears.

Let me now systematically review each document.

## 1. Major Contradictions and Inconsistencies

### 1.1 Comment Visibility: Fixed in v1.26, But Build Plan Still Stale

**Files:** SPEC.md §8.1, ARCHITECTURE.md §5, BUILD_PLAN.md Step 7.1

**The issue:** SPEC §8.1 was corrected in v1.26 to say that comment visibility is a *strict subset* of post visibility (you see a comment only if you see the post AND you're not blocked with the commenter). This is correct. However, BUILD_PLAN Step 7.1 still says simply: "visibility = the post's exactly." This directly contradicts the spec and will produce a working-but-wrong implementation.

**Why this matters:** If an AI builder follows BUILD_PLAN Step 7.1, they will implement comments as "same audience as post," which leaks comments to someone blocked with the commenter. The test case won't catch this because the test suite probably won't include a block scenario in Phase 7. This is exactly the kind of "gap" the documents warn about.

**Status:** `TODO.md` flags this as prompt 09 §L, so it's known, but it's not fixed yet.

### 1.2 The "Silent" Unfriend Confirmation

**Files:** SPEC.md §5.3, BUILD_PLAN.md Step 4.3

**The issue:** SPEC §5.3 requires the unfriend confirmation to say: *"They'll no longer see your posts or your about section. If you have friends in common, they can still see your name, photo and short bio—and any blog post tagged with an interest you both share."*

This is a *wonderful* piece of honest UX. But BUILD_PLAN Step 4.3 says only: "unfriend (silent)." The detailed confirmation text is not mentioned. A builder will implement "silent" as "no notification" and never add the warning text.

**Why this matters:** Users will unfriend someone, assuming full invisibility, and be surprised when their ex-friend still appears in mutual contexts. The confirmation text is the *only* thing that prevents that surprise. Omitting it from the build plan means it won't be built.

### 1.3 Retired Constants Still Live in Multiple Places

**Files:** ARCHITECTURE.md §4, §7.1; BUILD_PLAN.md §8.1, §13.4; TODO.md

**The issue:** SPEC §14 marks `BIO_CHANGE_COOLDOWN_HOURS` and `BIO_EDIT_GRACE_MINUTES` as **retired v1.16**, replaced by `REQUEST_HOLD_AFTER_PROFILE_CHANGE_HOURS`. Yet these constants still appear as active requirements in:

- ARCHITECTURE §4 (`profiles` table columns—they are *not* columns)
- ARCHITECTURE §7.1 (in the security argument)
- BUILD_PLAN §8.1 (step instructions)
- BUILD_PLAN §13.4 (rate limit discussion)

**Why this matters:** A builder following ARCHITECTURE will create database columns that the spec says don't exist. A builder following BUILD_PLAN will implement the wrong cooldown mechanism. This is a known issue (`TODO.md` warns "Do not start Phase 2 until 09 is done") but it's a serious landmine.

**Impact:** High—this will cause a real, reproducible bug if Phase 2 starts before prompt 09 runs.

### 1.4 The `/healthz` Endpoint Exemption

**Files:** SPEC.md §2, ARCHITECTURE.md §7.3

**The issue:** SPEC §2 says "No public (logged-out) pages except login/registration/invite-acceptance." ARCHITECTURE §7.3 creates an unauthenticated `/healthz` endpoint that returns "ok" and nothing else. The documents argue this is "not a page" because it returns no HTML, no template, no theme.

This is **technically correct** (a health check is not a "page"), but it's a *policy dodge*. The endpoint is still public, still reachable, and still reveals that the server is running. The distinction matters to an engineer but not to a user or a regulator.

**Why this matters:** The "no public pages" rule was a security and privacy principle. `/healthz` violates the *spirit* of that rule even if it follows the letter. The documents acknowledge this in CHANGELOG 1.24, saying the question was "answered" rather than "resolved." The real answer is that SPEC §2's list is simply incomplete—the privacy policy and accessibility statement are also linked from login pages, making them publicly accessible. The documents recognize this but haven't fixed it.

**Impact:** Low for the prototype, but it sets a precedent for "exceptions" that will accumulate.

## 2. Pitfalls and Practical Problems

### 2.1 The Operator Burden Is Severely Underestimated

**Files:** SPEC.md §11.2.1, §13.5, §7.2.3; BUILD_PLAN.md §10.1a, §17.3

**The issue:** The platform requires continuous, active operator work:

- **Hashtag vocabulary curation:** ~300 tags to start, plus ongoing suggestions. SPEC §11.2.1 *explicitly* says the operator is a single point of failure and that's "accepted." This is a *real* burden—anyone who's run a community knows that "accepting the burden" and *actually doing the work every week* are different things.
- **URL allowlist maintenance:** Every new domain request requires operator judgment against three categories plus an open-redirector check. This is not a one-time setup—the web changes constantly.
- **Reaction phrase curation:** The six criteria are a *significant* judgment load. SPEC §8.2.3 criterion 1 ("warm on the worst post it could land on") is emotionally demanding.
- **Moderation queue:** Reports, warnings, bans—all require human judgment. SPEC §13.2 says "formal policies/appeals are deferred," but the *work* is not deferred.
- **Theme set curation:** `THEME_SET` must be curated for accessibility, and new themes need contrast verification.
- **DEFAULT_AVATAR_SET curation:** The "original artwork" requirement means commissioning or creating avatars.

**Why this matters:** The documents are honest about this being a solo founder project. But they *systematically underestimate the ongoing cognitive load*. A founder with a day job cannot do all of this weekly. The "weekly digest" routine in BUILD_PLAN §17.3 includes "read the moderation/request queue"—but the moderation queue alone, if the platform has even 20 active users, will be non-trivial.

**The documents' own defense:** "This platform may stay at twenty friends forever, and that is an acceptable outcome" (ARCHITECTURE §7.3). This is honest, but it's also a *cop-out*. If the platform stays at twenty friends, the operator burden is manageable. If it grows to 50, it's already too much. The documents have no answer for that transition.

**Recommendation (if this were my project):** Build the **request queue batch reading** into the UI, not just the runbook. Make the operator's weekly routine *one page* that shows:
- All pending hashtag suggestions with frequency counts (so you can see patterns)
- All pending URL requests grouped by category
- All moderation reports grouped by severity

The current design makes the operator go into the Django admin, which is powerful but not optimized for this workflow. This is a *UX problem for the operator*, not just a "we'll handle it in the runbook" problem.

### 2.2 The Visibility Engine Is Correct, But the *Testing* Is Not Enough

**Files:** ARCHITECTURE.md §5, §9; BUILD_PLAN.md §4.2

**The issue:** The documents specify an *excellent* visibility engine with request-scoped memoization and bulk queries. The test suite described in ARCHITECTURE §9 is impressive.

**But:** The tests prove that the visibility engine returns the *correct* answers. They do **not** prove that no other code path bypasses the engine. The documents acknowledge this in BUILD_PLAN §0.6: "A test that cites the right section and asserts the wrong thing... Nothing in this plan catches it."

**Why this matters:** The visibility engine is the *single most important* piece of code in the entire platform. A single bug—one view that builds its own queryset, one template that checks friendship directly—and the privacy model is broken. The documents' solution is process discipline: "No template, page, list, count, notification, export, or job may decide for itself who can see something."

But **process discipline does not scale to an AI builder**. An AI model will, when asked to "make the feed faster," inline a query. The documents *anticipate* this and explicitly forbid it. But they rely on the founder noticing the forbidden pattern in code reviews—and the founder is not a developer.

**What's missing:** A **runtime assertion** that every permission check goes through the engine. This could be done with:
- A Django middleware that logs (or fails) any direct `Post.objects.filter` on user-visible content.
- A test that scans the codebase for import patterns that bypass the engine.
- A decorator on every view that asserts it only used the engine's querysets.

The documents have **none** of these. They rely entirely on discipline and code review.

**Recommendation:** Add a **static analysis check** to the build pipeline that rejects any direct access to `Post`, `Comment`, or `Reaction` models outside the visibility engine module. This is a few lines of Python with the `ast` module and would catch 90% of bypasses.

### 2.3 The "90-Day Deletion" Promise Has a 30-Day Backup Window

**Files:** SPEC.md §7.5, §4.7, §15.1; ARCHITECTURE.md §10

**The issue:** The documents are *admirably honest* about this: "deleted at 90 days, and purged from the last encrypted backup within 30 days after that." They explicitly say this is not "gone by day 120."

**But:** Users will not understand this distinction. The privacy policy may say it clearly, but the *user experience* will say "deleted after 90 days." The documents acknowledge this: "Claiming instantaneous total erasure while running nightly backups would be a lie; the documents say the true thing instead."

**Why this matters:** This is a **trust issue**. If a user deletes something and it reappears in a backup restore (even a disaster recovery restore), they will feel betrayed. The documents are correct that this is the industry-standard approach, but it's also the industry-standard *source of user confusion*.

**What's missing:** The UX should *show* the user what's happening. "Your post will be deleted from the platform on [date]. A copy may remain in encrypted backups for up to 30 more days." This is honest and upfront. The documents don't specify this UX.

### 2.4 The "No Counts" Rule Is Psychologically Impossible to Enforce

**Files:** SPEC.md §17, §12.2, §8.2

**The issue:** "No counts anywhere"—no follower counts, no reaction counts, no unread badges, no "3 new comments," no page numbers, no view counts.

This is a **beautiful principle** and I fully support it. But:

- **Notifications require a count** to know when to coalesce. SPEC §12.3 says "one per post per recipient, updating in place until it is read"—this inherently requires tracking whether the notification has been read.
- **The feed page** needs to know "are there older posts" to show the "Older posts →" link. This requires a count of remaining items.
- **The pagination system** in BUILD_PLAN §7.7.1 requires knowing how many items exist to know if there's a "next page."
- **The "friends page" filter** (§11.6) operates over a list of up to 300 names—this is technically a count, even if it's not displayed as one.

**Why this matters:** The documents' "no counts" rule is really "no counts displayed to users," but many operations *require* counts internally. The distinction is subtle and will be missed by a builder. An AI model asked to implement pagination will naturally compute a total count.

**What's missing:** A clear statement that "counts may exist internally but must never be rendered." The documents are ambiguous on this point.

### 2.5 The Accessibility Testing Cadence Depends on a Single Tester

**Files:** SPEC.md §16.5, §16.5.1; BUILD_PLAN.md §15.3, §17.3

**The issue:** The documents create an excellent accessibility testing regimen: continuous automated tests, milestone scans, and human passes by a qualified tester. The tester is booked at Step 15.3 and returns for re-audits.

**But:** This depends on **one specific person** continuing to be available. The documents acknowledge this: "an unavailable tester delays a re-audit; it does not break anything that already works."

**Why this matters:** Accessibility regressions are the *easiest* to introduce. A new interactive pattern (a new picker, a new dialog) will ship without a human pass if the tester is unavailable. The documents' answer is "the trigger stays open until it is run," but in practice, a solo founder will ship the feature and forget to run the audit.

**What's missing:** A **fallback plan** for when the tester is unavailable. The documents name "professional accessibility auditor" as the second choice, but that's a *different* person with a different schedule. There's no plan for "the tester is unavailable for three months."

## 3. Security and Privacy Concerns

### 3.1 The "Codes, Not Links" Policy Is Good, But...

**Files:** SPEC.md §4.6.1, BUILD_PLAN.md §2.5

**The issue:** Password reset and email verification use numeric codes that the user types in. This is excellent anti-phishing. However:

- **Invites are links** (the only exception). A new user has no session, so a link is unavoidable.
- **The checkable promise** is "WeeBee will never email you a link to log in or reset your password." This is true, but a user who receives a *fake* invite link (from a spoofed email) might still click it.

**Why this matters:** The codes-not-links policy is a **phishing mitigation**, not a phishing solution. A determined attacker will still send fake invites. The documents acknowledge this but don't provide a user education strategy beyond the promise.

**What's missing:** A **visual indicator** in the invite flow that tells the user "this is a real WeeBee invite." This could be:
- A key icon in the browser address bar (already present with HTTPS)
- A specific phrase in the invite email that's impossible for an attacker to guess
- A "verify this is WeeBee" page that shows the domain name in large type

### 3.2 The "No DMs" Policy Is Philosophically Sound but Creates a Gap

**Files:** SPEC.md §10.1

**The issue:** No direct messaging—person-to-person conversation belongs on external channels (phone, email, messengers). The platform's job is introduction and handoff.

**But:** This means **every conversation that starts on WeeBee must leave the platform** to continue. That's by design, but it creates:
- **A phishing vector** in the contact card: a bad actor could list a malicious messenger link.
- **A user friction point**: "I want to talk to Alice, but I need to switch apps."
- **A data leakage point**: external messengers may have their own tracking/privacy policies.

**Why this matters:** The documents are consistent about this, but the *user experience* will be frustrating. The "no DMs" policy is philosophical, and many users will want to message their friends. They will find workarounds (posting "email me at...", using comments as DMs, etc.).

**What's missing:** A **graceful handoff experience** that makes leaving the platform feel like a feature, not a limitation. The contact card should show *how* to reach someone, and the "request more access" flags (§10.5, if shipped) should make it easy to get a phone number or email.

### 3.3 The Block Mechanism Is Correct but the "Fully Mutually Invisible" Claim Is Overstated

**Files:** SPEC.md §5.4

**The issue:** "When A blocks B, neither appears in the other's discovery, suggestions, hashtag matches, mutual-friend lists, or introduction flows."

**But:** If A and B are both in a group conversation (a post with comments), B can still see A's *comments* on shared friends' posts? No—SPEC §5.4 says "Neither can see the other's comments or reactions anywhere, including on shared friends' posts."

However, **A's posts that B had already seen remain in B's memory**. The platform can't delete what's already been seen. The documents are honest about this ("defending against off-platform screenshots is out of scope") but it's worth flagging.

**Why this matters:** Users will expect a block to make someone "disappear" completely. It won't—the block prevents *future* interaction and *new* visibility, but past interactions are in memory. This is a common user expectation failure in social networks.

## 4. Technical and Architectural Concerns

### 4.1 The "One Server" Design Is Correct but the Backup Strategy Has a Gap

**Files:** ARCHITECTURE.md §10, §7.3

**The issue:** Nightly encrypted backups to off-server storage with 30-day retention. This is correct for the scale. But:

- **The backup key lives in the founder's password manager**, not on the server. This is good security but **creates a single point of failure**—if the founder loses the password manager, all backups are inaccessible.
- **The `verify_restore` job** runs weekly and restores the newest backup into a scratch database. This is excellent—it proves the restore path works. But it requires the backup credentials to be on the server, which is a different trust model than the "key off the server" principle.

**Why this matters:** The documents are internally consistent but the *combined* security posture is complex. A builder will need to carefully manage credentials in two places: the server (for `verify_restore`) and the password manager (for disaster recovery).

### 4.2 The Django Admin Is Used as the Operator Console

**Files:** ARCHITECTURE.md §3.1, BUILD_PLAN.md §13.3, SPEC.md §16.1.1

**The issue:** Django's admin is the operator console for moderation, vocabulary editing, etc. This is a deliberate choice: "the Django admin is the operator console for free."

**But:** The documents acknowledge in SPEC §16.1.1 that the admin is **not fully accessible**—it's held to a bounded subset (keyboard operability, visible focus, contrast, labelled fields, error text). The full WCAG AA standard is *not* claimed.

**Why this matters:** This is a **scope boundary** that's easy to miss. An accessibility statement that says "WCAG 2.1 AA" with a silent exclusion for the admin is the exact problem the honesty rule exists to prevent. The documents explicitly call this out and require the statement to name the carve-out.

**But:** The operator is the *only* person who uses the admin. If the operator is the founder (who is sighted and keyboard-competent), the admin's accessibility is a *non-issue*. The documents' own reasoning is sound, but it's a bit tortured.

### 4.3 The "Preformatted Post" Accessibility Exemption Is Correct but Will Be Overused

**Files:** SPEC.md §7.2.1, §16.3

**The issue:** Preformatted posts (for ASCII art, tables, diagrams) render in monospace and may scroll horizontally. This is a documented exception to the reflow requirement.

**But:** Users will use this as a "layout hack" for things that aren't actually diagrams. The composer explainer says "what the mode is for and its shortcomings," but users will ignore it.

**Why this matters:** The exemption is valid, but it will create a class of posts that are hard to read on phones. The documents acknowledge this and require the scroll region to be keyboard-scrollable and named, but they don't solve the *social* problem of users overusing the feature.

**What's missing:** A **warning** in the composer when a preformatted post is created, similar to the "this will scroll horizontally on narrow screens" warning. The documents mention "a brief explainer linked directly from the composer," but that's not a warning at the moment of posting.

### 4.4 The "No Infinite Scroll, No Load More" Policy Is Correct but Will Be Challenging

**Files:** SPEC.md §7.7.1

**The issue:** Long lists page with "Older posts →" and "← Newer posts" links. No infinite scroll, no "load more."

**This is excellent for accessibility**—infinite scroll is a disaster for keyboard users and screen readers. But:
- **Users expect infinite scroll.** They will be surprised by pagination.
- **The "Older posts →" link requires knowing there are older posts.** This requires a count of remaining items, which the documents forbid as a displayed count but allow internally.
- **The "← Newer posts" link appears only when you're on a page that's not the newest.** This requires knowing the current page position.

**Why this matters:** The pagination system is more complex than it looks. A builder will naturally implement traditional pagination with page numbers, which the documents explicitly forbid. The "prev/next" pattern requires tracking *state* (page number) without displaying it.

**What's missing:** A clear description of how pagination state is maintained. The documents say "ordinary page loads, ordinary back button," which implies the page number is in the URL. That's correct, but it needs to be explicit.

## 5. Operational and Maintenance Concerns

### 5.1 The Weekly Digest Is a Good Idea but Creates Alarm Fatigue

**Files:** ARCHITECTURE.md §7.3, BUILD_PLAN.md §5.7

**The issue:** The weekly digest sends a report "whether or not anything is wrong." This is intended to avoid alarm fatigue (if you only get emails when something's wrong, a quiet inbox looks the same as a dead server).

**But:** A weekly email that's always green will become *background noise*. The documents anticipate this and explicitly say "weekly rather than daily, deliberately." But the *real* problem is that when something *does* go wrong, the weekly digest will be the *only* signal—and if the server is dead, the digest won't be sent.

**Why this matters:** The documents acknowledge this and say "if the weekly digest doesn't arrive, that's the finding." This requires the founder to *notice* that a weekly email didn't arrive. In practice, this is a high cognitive load task.

**What's missing:** A **heartbeat monitor** (dead man's switch) that sends an alert if the *server* stops checking in. The documents acknowledge this in ARCHITECTURE §15 item 6 and BUILD_PLAN §17.3, saying it's "deferred with intent to build." This is the right answer, but it's a *gap* until it's built.

### 5.2 The "No External Monitoring at Launch" Decision Is Risky

**Files:** ARCHITECTURE §15 item 6, BUILD_PLAN §17.3

**The issue:** The founder decided **not** to use an external uptime/heartbeat service at launch. The reasoning: "At twenty users, the friends *are* the uptime monitor."

**This is a conscious tradeoff.** The documents are honest about it. But:
- **The trigger for building it** is "any public phase"—but the platform will *always* be public once it has any real users. The distinction between "friends-only" and "public" is a legal line, not an operational one.
- **The "friends will tell me" assumption** breaks if the platform grows beyond the founder's personal friends.
- **A friend reporting an outage requires them to *notice* the outage.** If the server goes down at 3 AM and comes back at 6 AM, nobody notices.

**Why this matters:** This is the single biggest operational risk. The documents are clear about it, and it's a reasonable tradeoff for a prototype. But it's worth flagging as a *real* gap.

### 5.3 The "Operator Request Queue" Is Under-Designed for Scale

**Files:** SPEC.md §13.5, BUILD_PLAN.md §17.3

**The issue:** The operator request queue handles hashtag suggestions, URL requests, bug reports, accessibility problems, and general feedback. The documents say "submissions are read in batches, no reply is sent."

**This is excellent for reducing operator burden.** But:
- **No reply to a user means they don't know if their request was accepted.** The documents say "an accepted change simply appears where it belongs," but a user won't notice a new hashtag in the picker.
- **No "pending" state means the user might submit the same request multiple times.**
- **The queue is a single list** without prioritization beyond "accessibility reports triaged ahead of feature requests."

**Why this matters:** The operator request queue is the *only* feedback mechanism. If it's poorly designed, users will feel unheard and leave. The documents' "no reply" policy is philosophically consistent (no notifications, no promises), but it's also *frustrating for users*.

**What's missing:** A **"your request was received" confirmation** that gives the user a sense of closure. This doesn't require a promise of action—just "we got it, we'll review it in our next batch." The documents say "the confirmation on submission has to do the whole job," but they don't specify what it says.

## 6. Accessibility Concerns

### 6.1 The "No Hover-Only" Rule Is Excellent but Missing in the Build Plan

**Files:** SPEC.md §7.5.1, §16.4; BUILD_PLAN.md Step 2.3, Step 16.5

**The issue:** SPEC §7.5.1 explicitly bans `title` attributes, `datetime` attributes, and any hover-only content. This is excellent accessibility.

**But:** BUILD_PLAN §2.3 only says "the helper returns the phrase and nothing else"—no mention of the `title`/`datetime` ban. A builder will naturally add a `title` attribute "to be helpful."

**Why this matters:** The ban is a *requirement*, not a suggestion. Omitting it from the build step means it won't be implemented. The documents rely on the human audit at Step 16.5 to catch it, but by then it's a fix, not a design choice.

### 6.2 The Screen-Reader Familiarization in Step 2.5 Is Good but Insufficient

**Files:** BUILD_PLAN.md §2.5

**The issue:** Step 2.5 says "Turn on VoiceOver and log in with your eyes closed once—it will be slow and strange; that is the point, and it takes ten minutes on a two-page site. This is familiarization, not verification."

**This is excellent.** But:
- **It's only on the login and reset pages.** The real accessibility challenges are in the feed, the composer, the profile page, the discover page, etc.
- **A sighted person doing a screen-reader pass for the first time will miss real failures** and chase false ones. The documents acknowledge this in SPEC §16.5.1 ("a daily screen-reader user is the preferred tester").

**Why this matters:** The founder will *feel* like they've tested accessibility after Step 2.5, but they haven't—they've only familiarized themselves with VoiceOver. The real testing comes at Step 16.5, but by then it's a long way away.

## 7. Data and Privacy Concerns

### 7.1 The "Backup Window" Is a GDPR Risk Even Though the Documents Are Honest

**Files:** SPEC.md §7.5, §4.7, §15.1; ARCHITECTURE.md §10

**The issue:** The documents are *admirably honest* about the 30-day backup window. But **GDPR Article 17 (Right to Erasure) requires erasure "without undue delay."** A 30-day window is probably acceptable, but it requires the privacy policy to state it clearly.

**The documents do this.** SPEC §15.1 says "the privacy policy states the backup window plainly." But:
- **The user-facing language** will inevitably simplify to "deleted after 90 days."
- **A GDPR complaint** would hinge on whether the backup window is "undue delay." 30 days is probably fine, but it's a risk.

**Why this matters:** This is a legal risk, not a technical one. The documents are in the right place, but the *implementation* (the privacy policy wording) will determine whether it's acceptable.

### 7.2 The "Invite Tree" Is a Potential Privacy Risk

**Files:** SPEC.md §4.3, §4.7

**The issue:** The invite tree records which account invited which. This is for "forensics and future analysis." When an account is deleted, the node is replaced by an "anonymized stub" ("deleted account #N invited X, Y").

**This is good privacy practice.** But:
- **The tree is permanent.** Even after deletion, the shape of the tree remains.
- **A determined adversary** could use the tree to infer social connections. If a cluster of deleted accounts are all invited by the same person, that person is identifiable.
- **The documents explicitly say** "any future accountability mechanism... is a separate, later decision." This means the tree could *become* a privacy risk if the operator later uses it for accountability.

**Why this matters:** The invite tree is a *deferred risk*. It's fine for v1, but the documents should have a clear policy on when (if ever) the tree is used.

### 7.3 The "No Tracking" Rule Is Good but the Email Provider Is a Weak Link

**Files:** SPEC.md §15.2, ARCHITECTURE.md §3.6

**The issue:** "No analytics trackers, no behavioral profiling, no third-party scripts"—this is excellent. But:
- **The email provider** (Postmark, Mailgun, or Amazon SES) sees all email content and metadata. The documents acknowledge this in ARCHITECTURE §3.6: "the provider sees addresses and email contents."
- **The privacy policy** must name the email provider as a processor.
- **The "transactional-only" provider** is chosen precisely to avoid marketing analytics.

**Why this matters:** This is a *trust transfer*. Users trust WeeBee, but they must also trust the email provider. The documents are honest about this, but it's a weak link in the privacy chain.

## 8. Assessment: Can This Be Built as Described?

### 8.1 The "Buildability" Assessment

**Likelihood:** **High**, with caveats.

**The documents are exceptionally buildable.** They specify everything: constants, behavior, architecture, testing, deployment, operations. The AI coding prompts in deliverable (d) will be the final piece.

**The real risk is not "can it be built" but "can it be maintained."** The operator burden is significant. The visibility engine is complex. The accessibility standards are demanding. The documents acknowledge all of this.

**What would make it unbillable?**
1. **The operator burden**—if the founder can't keep up, the platform will rot.
2. **The visibility engine complexity**—one bypass and the privacy model breaks.
3. **The accessibility requirements**—if the human tester isn't available, regressions will accumulate.

### 8.2 The "Solo Founder + AI" Model

**The documents' own premise** is that a solo founder with AI assistance can build this. **This is plausible for the initial build**, but:

- **AI models struggle with complex permission systems.** The visibility engine is the most complex part, and it's exactly where an AI is likely to make subtle errors. The documents' approach—dense tests, single source of truth—mitigates this.
- **AI models struggle with accessibility.** The documents' approach—shared partials, template smoke tests, human audit—mitigates this.
- **AI models struggle with operational discipline.** The documents' approach—runbooks, checklists, weekly digests—mitigates this.

**The biggest risk is that the founder becomes the "review bottleneck."** The documents are designed so the founder doesn't need to read code, only verify outcomes. But the verification steps are numerous and time-consuming. If the founder falls behind, the build stalls.

### 8.3 What Would I Change?

If I were the founder, I would:

1. **Add a "static analysis" check** for visibility engine bypasses. This is the single most important missing piece.
2. **Simplify the operator burden** by building a single operator dashboard, not relying on Django admin for everything. The current approach is "use what's free," but the operator needs a workflow, not just access.
3. **Add a "graceful handoff" experience** for the no-DM policy. Help users *want* to leave the platform to message.
4. **Build the external uptime monitor at launch, not later.** The documents' justification for deferring it is reasonable, but it's the one thing that will actually alert the founder if the server dies.
5. **Simplify the theme system.** `THEME_SET` and `DEFAULT_AVATAR_SET` are overdesigned. One or two themes and a simple avatar picker would be sufficient for v1.
6. **Make the "90-day deletion + 30-day backup" window visible to users.** A small note on the post saying "deletes in X days; backup copy retained for up to 30 more days" would manage expectations.
