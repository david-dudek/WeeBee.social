Here is a critique of the four documents, ordered from most critical to practical concerns. Every issue cites the exact file and section.

### 1. BUILD_PLAN.md and ARCHITECTURE.md are behind SPEC.md — major version mismatch

**Files:** BUILD_PLAN.md (header), ARCHITECTURE.md (header)  
**Sections:** BUILD_PLAN status line; ARCHITECTURE status line

**The problem:** SPEC.md is version **1.16**, but BUILD_PLAN.md explicitly says it is synced only to **v1.13–v1.15**, and ARCHITECTURE.md says the same. Because of this gap, the build plan is missing instructions for several major features that SPEC v1.16 introduced, and the architecture still describes database tables for mechanisms that the spec has retired.

**What this means in practice:** If you hand these documents to an AI builder, it will build the v1.15 version of the platform and miss critical v1.16 changes entirely.

**Specific v1.16 features missing from BUILD_PLAN:**
- The profile page’s four-tab structure (Blog, Pinned, Photos, About) and the rule that **feed posts now appear on the author’s Blog tab** (SPEC §9.1).
- The **friends page** with its filter box (SPEC §11.6).
- The **stated visibility line** on every post disclosing who can see it (SPEC §7.9).
- The **default avatar set** and profile-photo picker (SPEC §9.4).
- The **request hold** that blocks friend requests after a profile photo or short-bio change (SPEC §13.6).
- The 90-day expiry for **pending friend requests** and their frozen cards (SPEC §5.2).

**Specific v1.16 retirements still present in ARCHITECTURE.md §4:**
- The data model still describes `short_bio_changed_at`, `photo_changed_at`, `BIO_CHANGE_COOLDOWN_HOURS`, and `BIO_EDIT_GRACE_MINUTES`. SPEC v1.16 **retired these** and replaced them with `REQUEST_HOLD_AFTER_PROFILE_CHANGE_HOURS`, which works on the *push* (sending requests) rather than the *edit*.

**Recommendation:** Do not start building until BUILD_PLAN.md and ARCHITECTURE.md are updated to match SPEC v1.16 line-for-line.

### 2. SPEC contradicts itself on whether the friend-request card is “exactly” the basic-tier profile

**File:** SPEC.md  
**Sections:** §9.1 (basic-tier invariant) vs. §5.2 (friend-request card)

**The problem:** §9.1 states as an invariant that the friend-request card is “exactly §9.2’s basic tier and exactly §5.2’s friend-request card, built from one component.” But §5.2 explicitly says the card is a **snapshot** taken at send time—the photo and short bio are frozen, while the profile page shows **live** data that can change five minutes later. A snapshot and a live view cannot be the “exact same component” because one reads current database rows and the other reads frozen copies.

**In plain terms:** The spec is telling builders to build one reusable piece of code, but then giving it two conflicting data sources. If the builder follows the “one component” rule literally, friend-request cards will update live whenever the sender changes their photo, which destroys the anti-abuse snapshot mechanism.

### 3. SPEC contradicts itself on comment visibility vs. blocks

**File:** SPEC.md  
**Sections:** §8.1 vs. §5.4

**The problem:** §8.1 says a comment is visible to “exactly the people who can see the post — never more.” But §5.4 says that if Alice blocks Bob, **neither can see the other’s comments anywhere, including on shared friends’ posts.** That means even if Bob can see Charlie’s post, he cannot see Alice’s comment on it. So comment visibility is **smaller** than post visibility.

**In plain terms:** The “never more” sentence in §8.1 is factually wrong because blocks remove people from the comment audience. The architecture’s visibility engine (ARCHITECTURE §5) needs a separate `can_see_comment` check, but the architecture only lists `can_see_post` and `can_act`.

---

### 4. SPEC contradicts itself on timestamps in email

**File:** SPEC.md  
**Sections:** §4.6.1 vs. §12.3

**The problem:** §4.6.1 says security events (new-device login, password change, email change) carry **absolute timestamps “wherever they appear.”** §12.3 says **“Email carries no timestamp at all.”** If a security event is delivered by email—as a notification or warning—it must either carry a timestamp (violating §12.3) or not carry one (violating §4.6.1).

**In plain terms:** The documents give two hard rules that cannot both be true for the same email. You need to decide whether security-event emails are the narrow exception to the “no timestamps in email” rule.

### 5. “Full erasure” in SPEC ignores the backup-retention reality

**File:** SPEC.md  
**Sections:** §4.7 vs. ARCHITECTURE.md §10

**The problem:** SPEC §4.7 promises “full erasure of all data” on deletion, with no caveat. ARCHITECTURE.md §10 honestly records that encrypted backups retain data for **30 days**. This means deleted content still exists for up to a month.

**In plain terms:** If a user deletes their account and you tell them everything is gone, but you later disclose a 30-day backup retention in the privacy policy, the two statements conflict. The spec should acknowledge the backup window in §4.7 or §15.1 so the founder doesn’t accidentally over-promise.

### 6. The data model forgets to store the friend-request snapshot

**File:** ARCHITECTURE.md  
**Section:** §4 (friend_requests table)

**The problem:** SPEC §5.2 requires that when a friend request is sent, the requester’s **profile photo and short bio are frozen** into the request so they can’t be altered later to bypass screening. But ARCHITECTURE.md’s description of the `friend_requests` table only mentions “pending/declined with timestamps.” It never adds columns for the snapshotted image file and short-bio text.

**In plain terms:** An AI builder reading only the architecture document will build a friend-request table that points to the user’s *current* photo and bio. An abuser could send 20 “clean” requests, then change their photo to something offensive, and every unanswered card would instantly show the new offensive image.

### 7. The data model forgets gallery image ordering

**File:** ARCHITECTURE.md  
**Section:** §4 (images table)

**The problem:** SPEC §9.4 requires that gallery images have **author-arranged order** with “Move up / Move down” keyboard-accessible controls. But the `images` table described in ARCHITECTURE.md has no `position`, `sort_order`, or equivalent column.

**In plain terms:** Without an order field, the gallery will always display images in the order they were uploaded, and the user will have no way to rearrange them. The AI builder won’t know where to store the sequence.

### 8. “Ban an account” is never defined

**File:** SPEC.md  
**Section:** §13.2

**The problem:** The spec says the operator can “ban an account” as a moderation outcome, but it never defines what a ban actually does. Does it hide all the user’s content? Prevent them from logging in? Delete their data after a grace period? Keep their comments visible to others?

**In plain terms:** You have a button in the admin panel labeled “Ban,” but no document tells the builder what that button is supposed to do. Different AI models will guess differently—one might make it a permanent deletion, another might make it a reversible deactivation, and a third might only block new posts.

### 9. The accessibility audit asks too much of a non-developer founder

**File:** BUILD_PLAN.md  
**Section:** Step 16.5

**The problem:** Step 16.5 requires the founder to perform a full **screen-reader pass** with VoiceOver on Mac and iOS, a **keyboard-only pass**, and a **200% zoom / 320 px reflow pass** across every page type. While the plan mentions turning VoiceOver on, it does not teach the founder how to interpret what they hear.

**In plain terms:** Using a screen reader effectively requires knowing how to navigate by headings, landmarks, and form fields, and how to distinguish between a missing label and a polite live region. An IT professional who has never done this before will likely miss real WCAG failures or spend hours chasing false positives. The plan needs a short “how to listen for the five most common failures” cheat sheet, or this gate will be passed without actually catching bugs.

### 10. The AI “law-file guards” are fragile

**File:** BUILD_PLAN.md  
**Section:** Step 2.4

**The problem:** The plan proposes three mechanical guards to stop an AI from editing SPEC.md, ARCHITECTURE.md, BUILD_PLAN.md, and `constants.py`: AI tool deny-rules, a git pre-commit hook, and a constants tripwire test.

**In plain terms:** These sound robust, but they depend on the founder using exactly the right AI tool (Claude Code) and correctly installing a shell script hook. If the founder switches tools, uses a web interface, or the hook has a permissions issue, the guard fails silently. The tripwire test also creates a paradox: if the founder legitimately raises a cap (which §1.3 allows), the test fails, and the founder may not know whether to update the test file or if they’ve broken something.

### 11. Reactions on pinned posts may live forever

**File:** SPEC.md  
**Sections:** §7.6 vs. §8.2

**The problem:** SPEC §7.6 says comments on pinned posts still expire at 90 days, but §8.2 says nothing about reactions expiring. ARCHITECTURE.md §6’s `expire_content` job only deletes reactions when their parent post is deleted. Because pinned posts are never deleted, reactions on them could accumulate indefinitely.

**In plain terms:** A pinned post that stays up for two years could collect hundreds of reactions. Since the platform avoids counts, this may not seem like a problem, but it is a form of persistent state that the “statements expire” principle (§9.7) arguably should cover. The spec should clarify whether reactions die with comments or survive forever.

---

### 12. Hashtag gate is ambiguous for multi-tagged posts

**File:** SPEC.md  
**Section:** §11.3

**The problem:** §11.3 says a profile post tagged #x is visible to a viewer if the viewer also has #x. It does not explicitly say what happens when a post has **multiple** hashtags. Does the viewer need to match **all** of them or **any one** of them?

**In plain terms:** If David tags a post #hiking and #cooking, and Alice only has #hiking on her profile, can she see it? §11.4 implies “any shared tag,” but §11.3’s wording is singular (“tagged #x … the post carries #x”). An AI builder might implement an exact-match requirement and accidentally hide posts that should be visible.

---

### Summary

The most urgent issue is the **version mismatch**: BUILD_PLAN.md and ARCHITECTURE.md are not updated for SPEC v1.16, so they omit major features and describe retired database fields. After that, the spec contains several internal contradictions (comment visibility vs. blocks, the “exact same component” claim for request cards, and the timestamp-in-email conflict) that will confuse builders. Finally, there are practical gaps—the undefined “ban” behavior, missing gallery-order and request-snapshot columns, and an accessibility audit that assumes more assistive-technology experience than the founder’s background suggests.
